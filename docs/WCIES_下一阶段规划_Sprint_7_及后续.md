## 1.6 关键发现：平台发货时限已存在于数据中，但完全不可见

**这是 v3 新增的核心发现。**

### 事实

核查 OZON 官方规范（`docs/ozon-seller-openapi.json`）：

```json
"shipment_date": {
  "type": "string", "format": "date-time",
  "description": "Дата и время, до которой необходимо собрать отправление.
                  ... По истечении этого времени начнёт применяться новый тариф"
}
```

> 译文：**必须在此时间前完成拣货发货。超过此时间将开始适用新的费率（`tariffication`）。**

该字段**已经在我们的数据库里**——`orders.raw_data->>'shipment_date'`，4 单全部有值。
但**没有被提取成结构化字段，界面上也看不到**。

### 实测：真实订单的剩余时间

```
订单号         ERP状态      剩余时间（相对今天）
ORD00000001   EXCEPTION    ⚠️ 5 小时 31 分
ORD00000002   EXCEPTION    2 天 5 小时
ORD00000003   EXCEPTION    3 天 7 小时
ORD00000004   BACKORDERED  5 天 5 小时
```

**ORD00000001 只剩 5.5 小时，而系统对它没有任何提示。**

### 为什么这对"先售后采"是致命的

用户的流程是：

```text
OZON 订单进来
   ↓
系统：映射成功 → 库存为 0 → BACKORDERED + 缺货异常      ← 系统只到这里
   ↓
用户：看到订单 → 去网上采购货源 → 等快递到货
   ↓                                                    ← 这段时间在倒计时
用户：货到了 → 收进仓库（入库）                          ← 缺失 1
   ↓
系统：重试分配 → RESERVED → 拣货 → 出库 → 发 OZON 买家
   ↓
必须早于 shipment_date！                                 ← 缺失 2：系统不显示这个时限
```

**"先售后采"本质上是一场与平台时限的赛跑。** 而当前系统：
- 不显示还剩多少时间
- 不能在临近超时时告警
- BACKORDERED 无法区分"还没采购""已采购在途""来不及了"

超时的代价是**平台改按更高费率计费**（`tariffication`），即直接的经济损失。

## 1.7 已修复缺陷：待检库存被算作「可售」（v5）

**2026-09-12 发现并修复。**

用户在讨论收货方案时提到"商品转为另一种状态再逐渐入库"，
核查 `QC_PENDING`（待检）时发现该状态在界面上被算作可售。

### 事实

实测（收货 5 件为 `QC_PENDING`）：

| 界面显示 | 订单实际能否占用 |
|---|---|
| **可售 5.000** | **不能**（报 `INVENTORY_INSUFFICIENT_STOCK`） |

两处逻辑不一致：
- `inventory-query.service.ts` 聚合时**未按 condition 过滤**，把所有状态都算进可售；
- `reservation.service.ts` 占用时**硬编码只认 `SELLABLE`**（4 处）。

而 `docs/business-rules/inventory.md §5` 写明：

> Available = On Hand - Reserved - Picked - Safety Stock - **Unavailable Quantity**
> 其中不可销售 Condition 的库存：**不参与 SELLABLE Available**。

**代码漏掉了公式的最后一项**，`inventory.md` 的规则反而是对的。

### 影响

不止界面误导——它会让用户以为待检品可以卖，而订单实际分配失败。
若用户据此对平台承诺了库存，会造成超卖。

### 修复

可售量改为**只由 `SELLABLE` 余额推导**：`isSellableCondition()` + `sellableOf()`
两个共享函数同时用于列表行、库位明细、SKU 汇总三处，杜绝再次分叉。
`On Hand` 与「物理可用」**仍统计全部状态**（货确实在库），只有可售被排除。

回归测试 2 条（`inventory.integration.spec.ts`）：
1. `QC_PENDING` 计入 On Hand 但不计入可售，且占用返回 409；
2. 同仓同时有 `SELLABLE` 与 `QC_PENDING` 时不混合（On Hand 10 / 可售 4）。

# 2. 下一阶段的核心判断

## 2.1 链路中真正缺失的，是两件事

把用户要验证的链路与现有能力逐段对照：

| 环节 | 现有能力 | 状态 |
|---|---|---|
| **收货入库** | `POST /inventory/receive` 存在但标注 "future purchase-receipt primitive"；**无业务单据、无界面、无供应商** | ❌ **缺失 1** |
| 销售（订单→占用） | `ORDER_SYNC` + `ListingResolver` + `ReservationService` | ✅ |
| **平台时限** | 数据在 `raw_data` 里，**未提取、未展示、未告警** | ❌ **缺失 2** |
| 拣货 | Picking + 扫码校验 | ✅ |
| 出库 | Shipment/Package + 面单 | ✅ |

**"先售后采"这条路径系统已部分支持**：

```text
订单进来 → 映射成功但无库存 → BACKORDERED + ORDER_OUT_OF_STOCK  ✅
                              ↓ （用户采购，货到）
                        入库 → 重试分配 → RESERVED            ✅（重试已修，提交 880b0b7）
                              ↓
                          拣货 → 出库                          ✅
```

`retry-allocation` 今天刚修好（`880b0b7`），含"映射修复后重试"与"仍缺货正确落 BACKORDERED"。

### 一个已确认的设计要点：分配永远是手动的

核查代码确认（`order-ingestion.service.ts:149` 摄入时、`order.controller.ts:92` 手工重试），
**入库不会自动触发任何订单分配**。这对"先售后采"是**正确的**：

- 你为哪张订单买的货，就点哪张订单的「重试分配」——**由你决定归属，系统不猜**。
- 若做成"入库自动分配"，系统只能按库位/时间顺序挑订单，很可能把货分给错的订单，
  而 SKU 未启用序列号时**系统无法察觉分错了**。

代价：多张订单同时 BACKORDERED、库存只够部分时，需你按优先级手动逐张重试。
这是可接受的操作成本，远低于分错货的代价。

## 2.2 结论：Sprint 7 = 补上「入库」+「采购登记」+「时限可见」

三者缺一不可：

| 缺哪个 | 后果 |
|---|---|
| 只补入库 | 货收进来了，但不知道哪张订单最急，可能收完发现已经超时 |
| 只做时限 | 看得到倒计时，但没有把货收进系统的手段，仍然卡在 BACKORDERED |
| **缺采购登记** | **你不知道哪张订单已经去买了、哪张还没买——会重复采购或漏采购** |

### 采购登记才是「先售后采」的核心痛点（v4 新增）

用户明确指出：**收到订单后去采购，系统没有记录"已采购"，可能重复采购或漏采购。**

核查现状确认这是真实缺口：

- `order_items` **没有任何采购相关字段**（17 列全清单已核对）。
- 唯一的信号是 `fulfillment_status = BACKORDERED` + 一条 `ORDER_OUT_OF_STOCK` 异常。
- 但 `BACKORDERED` **混淆了至少三种需要不同处置的实况**：

```text
BACKORDERED  ← 同一个状态，三种含义
  ├─ 还没去采购        → 需要立刻行动（且时限在倒计时）
  ├─ 已采购，在途      → 等待，不要重复下单
  └─ 已到货，待入库    → 货在手上，尽快收货发出
```

**用户无法从界面上区分这三者，而它们的下一步动作完全不同。**

### 我之前推荐"不做采购单"是错的

v2 的理由是"用户是'先售后采'，采购单在补货聚合（Sprint 9）之前价值有限"。
**这个推理混淆了两个不同的东西**：

| | 采购计划（Planning） | 采购登记（Tracking） |
|---|---|---|
| 回答的问题 | **该买什么**（系统建议） | **买了吗**（人工登记） |
| 依赖 | 需要历史销量、安全库存、补货算法 | 零依赖，下单即登记 |
| 何时做 | Sprint 9（需聚合分析） | **Sprint 7（当前痛点）** |

用户要的是**登记**，我按**计划**的依赖去判断价值，因此得出了错误的结论。

### 时限与采购登记的关系

两者是同一条时间线上的两个维度，合起来才回答"现在该处理哪张单"：

```text
ORD00000001  剩 5.5h   未采购   ← 最紧急：马上买（可能来不及）
ORD00000005  剩 2 天   已采购   ← 等待到货，别重复下单
ORD00000003  剩 3 天   未采购   ← 今天该采购
ORD00000004  剩 5 天   已到货   ← 尽快收货入库
```

## 2.3 「有货的商品」这个诉求对范围的收敛

用户核心是管理**有货的商品**，而非全量。因此：
- **不需要**先解决 1323 条未映射（那是全量经营，属后续阶段）。
- **可以后移**商品/SKU 批量建档——用现有单条界面即可处理少量有货商品并验证链路。

# 3. Sprint 7 建议范围

## T1 平台发货时限可见 + 超时预警（先做，改动小、价值直接）

**为什么排第一**：用户手上就有一张 5.5 小时后到期的订单，而系统一声不吭。

**范围**：
1. `orders` 表新增结构化列 `shipment_deadline`（TIMESTAMPTZ，可空）+ Migration。
   - 由 OZON 映射器从 `shipment_date` 提取（**原始报文继续保留，符合 AGENTS.md §34**）。
   - 其他平台将来各自映射到同一字段。
2. 订单列表/详情展示剩余时间，按紧迫度分档（如：已超时 / <24h / <3天 / 正常）。
3. 订单右栏与首页看板加"临近超时"提醒。
4. 可选：超时前 N 小时进异常中心（`ORDER_SHIPMENT_DEADLINE_NEAR`，见决策 6）。

**注意**：这是**平台事实字段**，不是 ERP 状态——不得与 `erpStatus` 混淆（AGENTS.md §38）。

## T2 采购登记单（解决"已采了吗"）

**为什么**：`BACKORDERED` 无法区分"还没买"和"已经买了"，会导致**重复采购或漏采购**。
这是用户当前最直接的痛点。

**核心理念**：采购单在本期是**登记单据**（记录人的决定），不是**计划单据**（系统算该买什么）。
因此它零依赖、可立即实现——这正是 v2 误判的地方。

### 数据模型

```text
purchase_orders            采购单
  po_no                    业务编号（集中式序号，如 PO%06d）
  supplier_id              供应商（可空）
  source_note              货源说明（可空，一次性网购用）
  status                   ORDERED / PARTIALLY_RECEIVED / RECEIVED / CANCELLED
  ordered_at               下单时间
  expected_at              预计到货（可空，人工填）
  remark / created_by / created_at / updated_at

purchase_order_items       采购单明细
  po_id
  sku_id
  order_item_id            为哪张订单行采购（可空——备货采购无关联订单）
  quantity
  unit_cost                可空
  received_quantity        已收货数量（默认 0，由收货单累加）
  remark
```

### 「已采」如何呈现：**派生，不落库**

订单行的采购状态**不新增字段**，而是从采购单明细**派生**（符合 AGENTS.md §13
"派生值不得成为第二事实源"）：

| 派生状态 | 判定 | 界面 |
|---|---|---|
| **待采购** | 该订单行没有关联的未取消采购单 | 红色标记 + 「登记采购」按钮 |
| **已采购** | 关联采购单存在且 `received_quantity < quantity` | 蓝色标记 + 「PO-xxxx 已下单」+ 预计到货 |
| **已到货** | `received_quantity >= quantity` | 绿色标记 + 「待入库」/「已入库」 |

**收益**：状态永远与采购单事实一致，不存在"订单说已采、采购单说没采"的分裂。

### 防重复采购（用户明确提出的风险）

- **登记时检查**：为某订单行创建采购单前，若该行已有未取消的采购单，
  返回冲突并提示"该订单行已于 <时间> 登记采购（PO-xxxx）"，避免手滑下两单。
- **待采购视图**：订单列表增加筛选「待采购」= `BACKORDERED` 且无关联采购单。
  这是用户每天要看的列表——直接回答"今天该买什么"。

### 界面

- **订单页**：订单行显示采购状态；BACKORDERED 行右栏给「登记采购」按钮
  （预填 SKU + 数量 + 关联该订单行）。
- **采购页**（新建「采购」一级菜单）：采购单列表（筛选：状态/供应商/日期/关联订单）
  → 新建/编辑 → 明细行 → 标记已下单。
- 也支持**备货采购**（不关联订单行），用于常规备货。

## T3 供应商与货源（轻量）

- `suppliers` 表（编码 / 名称 / 联系人 / 电话 / 备注 / 状态）+ 标准 CRUD +
  零引用删除（沿用决策 0003 模式）。编码需新增业务前缀（如 `SUP%04d`），
  按 `master-data.md §1` 表格登记。**仅用于可复用的固定供应商**。
- 采购单上 `supplier_id` 与 `source_note` **二选一且都可空**（见决策 1）：
  一次性网购只需在 `source_note` 写一行（如"淘宝 订单号 12345678"），**不进主数据**。

## T4 收货入库单（本 Sprint 核心）

**为什么与采购单分开**：采购单是**意图**（可取消、不影响库存），收货单是**不可逆的库存事实**。
混在一张单据里会让状态机同时承担两种语义——这与 Order 与 Shipment 分离是同一个道理。

### 数据模型

```text
purchase_receipts          收货单
  receipt_no               业务编号（如 PR%06d）
  purchase_order_id        来源采购单（可空——也可能直接收货）
  supplier_id              供应商（可空，默认从采购单带过来）
  source_note              货源说明（可空）
  warehouse_id             收货仓库
  status                   DRAFT / RECEIVED / CANCELLED
  received_at              实际收货时间
  remark / created_by / created_at

purchase_receipt_items     收货单明细
  receipt_id
  purchase_order_item_id   来源采购明细（可空）
  sku_id
  quantity                 本次实收数量
  unit_cost                单位成本（可空）
  bin_id                   目标库位（可空 → 用 ensureDefaultBin）
  remark
```

**支持分批到货**：一张采购单可对应多张收货单，`received_quantity` 累加。

### 状态机

```text
采购单：ORDERED → PARTIALLY_RECEIVED → RECEIVED
            └──→ CANCELLED（未收货前可取消，不影响库存）

收货单：DRAFT → RECEIVED（不可撤销，修正走库存调整）
          └──→ CANCELLED
```

### 关键约束

- **确认收货**才写库存：`PurchaseReceiptService.confirm()` → 逐行调
  `InventoryService.receiveStock()`。采购模块**绝不直接改 `inventory_balances`**
  （`工程架构文档:1005-1008` 明令）。
- 整单一个事务，任一行失败全部回滚。
- 重复确认幂等（`idempotencyKey = PURCHASE_RECEIPT:<receiptId>`）。
- `RECEIVED` 后不可改数量——库存已入账，改动必须走调整以保持流水可追溯。

### 界面

收货单列表（筛选：来源采购单/状态/日期/仓库）→ 新建（可直接从采购单「生成收货单」并预填）
→ 明细（实收数量可少于采购数量）→ **确认前预览**（将入库哪些 SKU、各多少、入到哪个库位）。

## T5 端到端链路验证（本 Sprint 验收）

用户明确要求验证的链路，写成集成测试 + 手工验收脚本。

**链路 A：备货销售（先有货）**

```text
1. 建立 Product + SKU（或复用 SKU000010001）
2. 建立平台映射（已有的「人工映射」入口）
3. 建收货单（或「采购单 → 收货单」）：供应商 X → 仓库 ZG-01 → SKU × N → 确认收货
       ↓ 断言 inventory_balances.on_hand = N
       ↓ 断言 inventory_transactions 有流水，reference = 该收货/采购单
4. 订单进来 → 占用库存
       ↓ 断言 reservation RESERVED，available 减少，deadline 可见
5. 拣货 → 扫码
       ↓ 断言 Reserved → Picked
6. 发货
       ↓ 断言 On Hand 减少，订单行 SHIPPED
```

**链路 B：先售后采（用户的主营模式）——本 Sprint 的重点验收**

```text
1. 订单进来，库存为 0
       ↓ 断言 行 BACKORDERED + ORDER_OUT_OF_STOCK 异常
       ↓ 断言 订单行派生采购状态 = 待采购
2. 点「登记采购」→ 生成采购单（关联该订单行）
       ↓ 断言 订单行派生状态 = 已采购
       ↓ 断言 重复登记被拒（防重复采购）
3. 货到 → 从采购单生成收货单 → 确认收货
       ↓ 断言 inventory_balances.on_hand = N
       ↓ 断言 采购单 received_quantity 累加、状态 → RECEIVED
       ↓ 断言 订单行派生状态 = 已到货
4. 重试分配
       ↓ 断言 RESERVED
5. 拣货 → 发货（同链路 A）
```

链路 A 的第 4–6 步代码已存在且有测试覆盖；本 Sprint 要验证的是

拣货扫码能否找到、可用量计算是否正确。

# 5. 需要用户决策的点

## 决策 1：供应商是否必填（已据用户业务澄清修正）

**用户业务形态**：大部分采购是**一次性网购**（接到订单后去网上买），卖家每次可能不同。
**因此原推荐（必填）作废。**

强制建供应商档案的后果：供应商主数据被几百个"只用一次的淘宝卖家"淹没，
真正要复用的固定供应商反而找不到；且每次收货都要先建档案，是纯粹的录入摩擦。

**修正后的方案**：

| 采购形态 | 记录方式 |
|---|---|
| 固定/反复合作的供应商 | 建 `suppliers` 档案，收货单引用 `supplier_id`；将来可据此做补货计划 |
| 一次性网购 | 只在 `source_note` 填一行（如"淘宝 订单号 12345678"），**不进主数据** |

- **A（推荐）**：两者都可空，UI 二选一引导，都空时提示但不阻断。
- **B**：二选一至少填一个（更严格的可追溯性，代价是每次收货多一步）。

推荐 A：`source_note` 近乎零摩擦，实际不会有人跳过；强制反而促使用户乱填。
若将来财务/审计要求可追溯，再收紧为 B 也不影响表结构。

## 决策 2：采购单与收货单**分开**（已修正，不再是"做不做"）

**用户澄清后，v2 的"不做采购单"推荐作废。** 采购登记是当期痛点，必须做。
本决策改为：**采购单与收货单是分开的两张单据，还是合并成一张？**

- **A（推荐）**：**分开**。采购单 = 意图（可取消、不影响库存）；收货单 = 已发生的
  库存事实（不可逆）。两者生命周期不同，混在一张单里会让状态机同时承担两种语义——
  与 Order / Shipment 分离同理（AGENTS.md §37 冻结规则）。支持分批到货。
- **B**：合并。少一张表、少一步操作，但"已采购未到货"与"已到货"必须揉在一个状态里，
  且取消采购与冲销库存会纠缠；将来加供应商对账、采购退货时会更难拆。

推荐 A。若嫌操作繁琐，用「从采购单生成收货单」一键预填来降低负担，而不是合并单据。

## 决策 3：单位成本与移动加权平均
架构文档 §86 规定「采购成本采用移动加权平均，入库时更新成本」，而 `moving_average_cost`
字段注释写的就是"采购 Sprint 实现"——**本 Sprint 就是那个 Sprint**。
- **A（推荐）**：采购单/收货单记 `unit_cost`，确认收货时更新 `moving_average_cost`。
- **B**：本期只记 `unit_cost`，不计算平均成本（将来补算会缺历史数据）。

**注意**：选 A 会改变 SKU 成本语义，必须同步更新 `master-data.md` 与 `inventory.md`
（AGENTS.md §86 把 Cost 列为必须同步文档的业务）。

## 决策 4：新增库存引用类型

（`inventory/enums/inventory.constants.ts:76`）。收货入库需新增（如 `PURCHASE_RECEIPT`）

不加的后果：收货流水与手工调整无法区分。

## 决策 5：平台库存"双轨期"是否接受

- **B**：放在「库存」菜单下。

## 决策 9：收货作业方式（扫码 / 库位 / 分批）

用户提出四个具体问题：收货如何扫码、没有既有库位时如何定库位、库位满了怎么办、
商品尺寸差异大如何判断放得下。逐条给结论。

### 9.1 扫码入库（用户要求，可行）

**现状**：`findByBarcode` 已存在（`barcode.service.ts`），拣货与拦截已在用这条链路；
但**收货接口目前收的是 `skuId`（UUID），不接受条码**。

**方案**：收货单明细录入时支持扫码——前端扫码 → 调条码解析 → 得到 SKU → 加入明细。
后端需补一个「按条码查 SKU」的查询接口（现有 `findByBarcode` 是服务层方法，未暴露 HTTP）。

**提示**：SKU 的内部条码规则是 `WCSKU%08d`（`master-data.md §1`）；
若商品自带厂商条码（EAN/GTIN），也可录入为附加条码，扫码时一并匹配。

### 9.2 库位如何确定（分三种情况，都不是"猜"）

现有规则（`inventory-dimension.ts:28-60`）已经给出了正确的基础：

> 收货时 `binId` 可省略**仅当该仓没有库位**——此时自动用虚拟 `DEFAULT` 库位；
> **仓库已有库位则必须显式指定**。

据此分三种情况：

| 情况 | 处理 |
|---|---|
| A. 仓库还没建库位 | 收货时留空 → 自动落到 `DEFAULT` 虚拟库位。**适合"先收进来再说"** |
| B. 有库位、知道放哪 | 收货时选/扫具体库位 |
| C. 有库位、暂时不确定 | 先收进 `DEFAULT`（若尚无则建一个），**之后再 `MOVE_BIN` 上架** |

**注意 C 需要确认**：当前 `DEFAULT` 只在「仓库无任何库位」时才允许自动创建。
若要在**已有库位的仓库**里也保留一个"待上架区"，需要放宽这条规则，
或显式建一个名为 `STAGING` 的暂存库位。**这是决策点。**

### 9.3 效率问题（用户担心的"扫一个就得放一个"）

**建议流程与用户设想一致：先收货、后上架。** 即：

```text
1. 收货：扫码 SKU + 数量（不指定库位，或统一指定 STAGING/DEFAULT）
        → 库存状态：On Hand 增加，落在暂存库位
2. 上架：后续用 MOVE_BIN 逐个移到正式库位
```

但**必须确认一个前提**（见 9.5）：`MOVE_BIN` 是**单 SKU 单库位间**的移动
（`MoveBinRequestDto`：`skuId + fromBinId + toBinId + quantity`），
一次针对一个 SKU，因此上架同样是逐个 SKU 操作。若要"扫一次移动一批"需要新能力。

### 9.4 库位容量：不建议做，理由如下

**现状**：`warehouse_bins` **没有任何容量字段**（12 列已核对）；
SKU 有 `length_mm / width_mm / height_mm / volume_mm3`，但 `master-data.md` 明确
长宽高是**选填**（"全有或全无"），实际大部分 SKU 不会填。

**结论：现阶段不应做自动容量校验**，三个理由：

1. **数据不足**：多数 SKU 缺尺寸，算了也不准，反而给出错误的安全感。
2. **形态差异**：软包装（衣物）可以挤压、可以叠放；硬箱（积木盒）不能。
   体积算不出来的情形远多于算得出来的。
3. **AGENTS.md §74**：禁止为未明确的需求引入复杂化。

**建议**：库位容量**由人判断**，系统只提供辅助信息——录入时显示该库位**当前已放的
SKU 与数量**，让人自己决定。这是"给人信息"而不是"替人决策"。

若将来确有需要，可在 `warehouse_bins` 加 `capacity_note`（自由文本，如"最多 20 箱"）
作为提醒，而非硬性校验。

### 9.5 收货是否需要「待上架」这个中间状态

用户提到"商品转为另一种状态，再逐渐入库"。需要区分两种做法：

| 做法 | 含义 | 评价 |
|---|---|---|
| **A. 用暂存库位** | 收货进 `STAGING`/`DEFAULT` 库位，之后 `MOVE_BIN` 上架 | **推荐**：库位是已有维度，无需新状态；库存事实清晰（货在暂存区） |
| **B. 用 `QC_PENDING` 状态** | 收货为待检，之后再转 `SELLABLE` | 谨慎：`QC_PENDING` 语义是"待质检"，用于上架暂存会污染该字段含义 |

**推荐 A**：暂存是**位置**问题，不是**质量**问题，用库位表达更准确。

**A 的前提**：需要一个"待上架区"库位（见 9.2 情况 C），且若希望"扫一次上架一批"
需新增批量移动能力（见 9.3）。

### 9.6 本节结论汇总

| 问题 | 结论 | 需实现 |
|---|---|---|
| 扫码收货 | 可行，链路已具备（拣货/拦截在用） | 暴露"按条码查 SKU"的 HTTP 接口 |
| 库位确定 | 沿用现有三分支规则 | 「有库位的仓也用暂存位」需放宽规则或建 `STAGING` 位 |
| 效率 | 先收货进暂存、后上架 | 暂存位 + （可选）批量移动 |
| 容量 | **不做自动校验**，只显示现状供人判断 | 明细录入时显示该库位已有内容 |

## 决策 10：条码与 SN——新到货没有条码怎么办（v6 新增）

用户提出：**扫码扫的是我们自己的条码，但刚到的货没有条码**；
另有商品**要用自己的 SN 管理**。

### 10.1 现有能力（已核实）

| 能力 | 现状 |
|---|---|
| 一个 SKU 多个条码 | ✅ 支持（`sku_barcodes`，最多一个 `is_primary`，DB 部分唯一索引保证） |
| 条码类型 | ✅ 5 种：`EAN / GTIN / MANUFACTURER / INTERNAL / OTHER` |
| 生成内部条码 | ✅ `POST /skus/:skuId/barcodes/generate-internal`，规则 `WCSKU%08d` |
| SN 管理 | ✅ `skus.serial_tracking` 开关 + `inventory_serials` 表 |
| 收货时 SN 校验 | ✅ **强制**：SN 商品必须提供与数量一致的 SN 列表，非 SN 商品禁止提供 |
| 拣货时 SN 校验 | ✅ **强制**：SN 商品必须扫 SN，且必须匹配该库位已有 SN |
| 打包/发货 SN | ✅ 已接入（`packing.service.ts` / `shipment-ship.service.ts`） |

**结论：SN 的后端链路是完整的**（收货→拣货→打包→发货全程校验）。

### 10.2 问题一：新到货没有条码

**这不是缺陷，是必然**——新商品第一次到货时，系统里根本没有它的条码。

**方案：收货前/收货时补建条码，分两步**

```text
供应商给的商品条码/厂商条码
  → 录入为该 SKU 的条码（类型 EAN / MANUFACTURER）
  → 之后收货、拣货都能扫它

供应商没给条码，或条码不可用
  → 生成内部条码 WCSKU%08d（已有接口）
  → 打印标签贴上（打印能力见 10.3）
  → 之后扫内部条码
```

**关键点**：一个 SKU 可以**同时**有厂商条码和内部条码（多码支持已具备），
所以「有厂商码就扫厂商码、没有就贴内部码」两条路都通，不需要二选一。

**需实现**：收货界面允许**当场补建条码**（现在条码只能在 SKU 管理页维护）。
建议做法：收货扫码框输入一个未知条码时，提示"该条码未绑定任何 SKU，
是否绑定到当前选中的 SKU？"——避免跑去别的页面。

### 10.3 缺口：没有标签打印能力

全局搜索确认：**系统当前没有任何 SKU 标签打印功能**（只有发货面单的上传/查看）。

没有打印机时，`WCSKU00000001` 这个字符串无法变成可扫的标签。

### 10.3.1 用户提出的方向：独立打单子系统（v7 修正）

用户提出"集成一个打单子系统，用于打印条码和面单"，理由是**之后还要接入快递系统打面单**。
这个判断是对的——**两种打印需求确实可以合并**。以下是核实到的事实与建议。

#### 事实一：OZON 面单不需要"打单系统"也能拿到

`docs/ozon-seller-openapi.json` 确认 OZON 提供官方面单接口：

| 接口 | 用途 |
|---|---|
| `POST /v2/posting/fbs/package-label` | **同步**返回 PDF（≤20 个发货单/次）。仅限 `awaiting_deliver` 状态；任一单失败则全部不生成；建议打包后 45–60 秒再请求 |
| `POST /v2/posting/fbs/package-label/create` + `/get` | **异步**批量生成，返回多个任务（大/小标签分开） |

**结论**：OZON 的面单是**平台生成 PDF**，我们只需下载并打印。
所以「打单系统」对我们而言不是"生成面单"，而是"**把 PDF 送到标签打印机**"。

#### 事实二：真正的缺口是"浏览器到打印机"这一段

当前面单流程是：平台 PDF → 上传/存对象存储 → 签名 URL → **浏览器打开 → 人工打印**。
SKU 标签则连生成都还没有。

两种打印对象的差异：

| | 面单（OZON 生成） | SKU/库位标签（我们生成） |
|---|---|---|
| 内容来源 | 平台 PDF，固定尺寸 | 我们自己排版（Code128 条码） |
| 打印方式 | A4 或标签纸，浏览器可打 | 标签纸（如 40×30mm），**浏览器打印很别扭** |
| 量 | 每单一张 | 批量（一次几十上百张） |

**标签纸打印走浏览器是很差的体验**：需要精确设置纸张尺寸、边距、缩放，
且不同打印机驱动差异大。这正是用户直觉认为需要"打单系统"的原因，**这个直觉是对的**。

#### 事实三：三种技术路线（不引入新依赖的前提下）

| 路线 | 做法 | 优点 | 代价 |
|---|---|---|---|
| **A. 纯浏览器打印**（零新增） | 生成 PDF/HTML → 浏览器打印对话框 | 无需任何部署，跨平台 | 标签纸排版需人工设置；无法免驱；批量体验差 |
| **B. 本地打印代理**（推荐） | 一个跑在仓库电脑上的小程序，监听 localhost，接收打印任务并直接驱动打印机（ESC/POS、TSPL、ZPL） | **免驱、静默打印、支持标签纸**；Web 只管发任务 | 需要一个本地进程 + 安装说明；需确定打印机指令集 |
| **C. 打印服务端** | 后端直接把任务发到网络打印机（IP 直连） | 仓库电脑无需装东西 | 要求打印机支持网络协议；**跨网/云部署时不可行**（打印机在局域网，服务器在云上） |

**推荐 B**，理由：
1. **部署现实**：仓库打印机在局域网，服务器可能在云上——路线 C 在云部署下走不通。
2. **技术成熟**：本地代理是打单类工具的标准做法（市面打单软件多为此形态）。
3. **不违反项目约束**：它是**独立的本地小程序**，不进入 Monorepo、不改变 Web/API 架构
   （AGENTS.md §4 禁止新增顶级架构层，故**不放进 `apps/`**）。

#### 边界（重要）

**建议现在不做，只把接口留出来。** 理由：

1. **Sprint 7 的验证目标不需要它**。先用浏览器打印或导出文件跑通
   「入库→销售→拣货→出库」，验证业务链路；打印是**操作体验**问题，不阻塞链路验证。
2. **本地代理需要确定打印机型号与指令集**才能写。这个信息现在没有，
   凭猜测写的驱动必然要返工（AGENTS.md §88 同类原则：不猜外部接口）。
3. **快递系统尚未选定**。用户提到"之后还可能接入快递系统"——等确定用哪家
   （或其面单格式），代理的输入格式才能一次定对。

**建议的落地顺序**：

```text
Sprint 7：生成条码 + 导出可打印文件（PDF），先用现有打印机/第三方工具
   ↓（同时收集：打印机型号、标签纸规格、快递系统选型）
Sprint 8+：按确定的硬件与快递系统，实现本地打印代理
```

**现在要做的准备**：把"打印任务"抽象成一个**输出格式约定**（谁生成、什么格式、
谁消费），这样将来接代理时 Web 端改动最小。这一点纳入 Sprint 7 的设计即可。

**注意**：条码规格应为 **Code128**（决策 0007），内部条码 `WCSKU` 含字母，不能用 EAN-13。

### 10.4 问题二：用自己的 SN 管理

**已支持**，流程如下：

```text
1. SKU 上开启「SN 管理」（serial_tracking = true）
2. 收货时逐件录入/扫描 SN，数量必须与 SN 个数一致
       ↓ 系统校验：不符直接拒绝（InventorySerialInvalidError）
       ↓ 写入 inventory_serials（status = IN_STOCK，绑定库位）
3. 拣货时扫 SN：必须匹配该库位存在的 SN，否则报错
4. 打包/发货：继续按 SN 校验
```

**SN 从哪来**——两种，取决于商品：

| 情况 | SN 来源 |
|---|---|
| 供应商商品自带序列号（如手机 IMEI、手表机身号） | **扫商品上的 SN**，这是最自然的做法 |
| 商品没有 SN，但你要自己管 | 需要**自建 SN 规则**并打印标签（见 10.5） |

**注意**：系统**没有 SN 自动生成能力**（已核实：全仓库无 `generateSerial` 类方法）。
现有设计假设 SN 由外部提供（厂商序列号）。若要自建 SN，属于新增能力。

### 10.5 决策点：自建 SN 是否需要

- **A（推荐先不做）**：只用**厂商自带 SN**。适用于手机、数码等本身有序列号的商品。
- **B**：需要**自建 SN 生成**。适用于无序列号但你要逐件追踪的商品（如高值单品）。
  需要新增：SN 生成规则（如 `{SKU}-{序号}`）+ 批量生成 + 标签打印（与 10.3 同一套）。

**建议**：先确认这类商品**占多少**。若只是少数高值商品，A 足够；
若大量商品需要逐件追踪，B 才值得做——但那是独立的工作量。

### 10.6 本节结论汇总

| 问题 | 结论 | 需实现 |
|---|---|---|
| 新货没条码 | 收货前补建条码即可（多码已支持） | 收货界面**当场补建条码**的入口 |
| 内部条码 | 生成接口已有 | **标签打印/导出**（10.3，建议先做导出） |
| 用自己的 SN | **后端链路完整**（收货→拣货→发货全程校验） | 无（SN 由商品自带，扫码录入） |
| 自建 SN | 系统**不支持自动生成** | 需你确认是否需要（10.5） |
| 打印子系统 | **方向正确**；推荐"本地打印代理"，但**现在不做** | Sprint 7 只定义输出格式约定（10.3.1） |

**待收集的信息**（决定打印代理能否一次写对）：
1. 标签打印机**型号与指令集**（TSPL / ZPL / ESC-POS）
2. 标签纸**规格**（如 40×30mm）
3. 快递系统**选型**（若走快递而非 OZON 面单）
