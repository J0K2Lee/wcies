## 1.6 关键发现：平台发货时限已存在于数据中，但完全不可见

**这是 v3 新增的核心发现。**

### 事实

核查 OZON 官方规范（`docs/ozon-seller-openapi.json`）：

```json
"shipment_date": {
  "type": "string", "format": "date-time",
  "description": "Дата и время, до которой необходимо собрать отправление.
                  ... По истечении этого времени начнёт применяться новый тариф"
}
```

> 译文：**必须在此时间前完成拣货发货。超过此时间将开始适用新的费率（`tariffication`）。**

该字段**已经在我们的数据库里**——`orders.raw_data->>'shipment_date'`，4 单全部有值。
但**没有被提取成结构化字段，界面上也看不到**。

### 实测：真实订单的剩余时间

```
订单号         ERP状态      剩余时间（相对今天）
ORD00000001   EXCEPTION    ⚠️ 5 小时 31 分
ORD00000002   EXCEPTION    2 天 5 小时
ORD00000003   EXCEPTION    3 天 7 小时
ORD00000004   BACKORDERED  5 天 5 小时
```

**ORD00000001 只剩 5.5 小时，而系统对它没有任何提示。**

### 为什么这对"先售后采"是致命的

用户的流程是：

```text
OZON 订单进来
   ↓
系统：映射成功 → 库存为 0 → BACKORDERED + 缺货异常      ← 系统只到这里
   ↓
用户：看到订单 → 去网上采购货源 → 等快递到货
   ↓                                                    ← 这段时间在倒计时
用户：货到了 → 收进仓库（入库）                          ← 缺失 1
   ↓
系统：重试分配 → RESERVED → 拣货 → 出库 → 发 OZON 买家
   ↓
必须早于 shipment_date！                                 ← 缺失 2：系统不显示这个时限
```

**"先售后采"本质上是一场与平台时限的赛跑。** 而当前系统：
- 不显示还剩多少时间
- 不能在临近超时时告警
- BACKORDERED 无法区分"还没采购""已采购在途""来不及了"

超时的代价是**平台改按更高费率计费**（`tariffication`），即直接的经济损失。

# 2. 下一阶段的核心判断

## 2.1 链路中真正缺失的，是两件事

把用户要验证的链路与现有能力逐段对照：

| 环节 | 现有能力 | 状态 |
|---|---|---|
| **收货入库** | `POST /inventory/receive` 存在但标注 "future purchase-receipt primitive"；**无业务单据、无界面、无供应商** | ❌ **缺失 1** |
| 销售（订单→占用） | `ORDER_SYNC` + `ListingResolver` + `ReservationService` | ✅ |
| **平台时限** | 数据在 `raw_data` 里，**未提取、未展示、未告警** | ❌ **缺失 2** |
| 拣货 | Picking + 扫码校验 | ✅ |
| 出库 | Shipment/Package + 面单 | ✅ |

**"先售后采"这条路径系统已部分支持**：

```text
订单进来 → 映射成功但无库存 → BACKORDERED + ORDER_OUT_OF_STOCK  ✅
                              ↓ （用户采购，货到）
                        入库 → 重试分配 → RESERVED            ✅（重试已修，提交 880b0b7）
                              ↓
                          拣货 → 出库                          ✅
```

`retry-allocation` 今天刚修好（`880b0b7`），含"映射修复后重试"与"仍缺货正确落 BACKORDERED"。

### 一个已确认的设计要点：分配永远是手动的

核查代码确认（`order-ingestion.service.ts:149` 摄入时、`order.controller.ts:92` 手工重试），
**入库不会自动触发任何订单分配**。这对"先售后采"是**正确的**：

- 你为哪张订单买的货，就点哪张订单的「重试分配」——**由你决定归属，系统不猜**。
- 若做成"入库自动分配"，系统只能按库位/时间顺序挑订单，很可能把货分给错的订单，
  而 SKU 未启用序列号时**系统无法察觉分错了**。

代价：多张订单同时 BACKORDERED、库存只够部分时，需你按优先级手动逐张重试。
这是可接受的操作成本，远低于分错货的代价。

## 2.2 结论：Sprint 7 = 补上「入库」+ 让「时限」可见

两者缺一不可：
- **只补入库**：货收进来了，但不知道哪张订单最急，可能收完发现已经超时。
- **只做时限**：看得到倒计时，但没有把货收进系统的手段，仍然卡在 BACKORDERED。

**且时限的改动量远小于入库**，可以更早交付价值。

## 2.3 「有货的商品」这个诉求对范围的收敛

用户核心是管理**有货的商品**，而非全量。因此：
- **不需要**先解决 1323 条未映射（那是全量经营，属后续阶段）。
- **可以后移**商品/SKU 批量建档——用现有单条界面即可处理少量有货商品并验证链路。

# 3. Sprint 7 建议范围

## T1 平台发货时限可见 + 超时预警（先做，改动小、价值直接）

**为什么排第一**：用户手上就有一张 5.5 小时后到期的订单，而系统一声不吭。

**范围**：
1. `orders` 表新增结构化列 `shipment_deadline`（TIMESTAMPTZ，可空）+ Migration。
   - 由 OZON 映射器从 `shipment_date` 提取（**原始报文继续保留，符合 AGENTS.md §34**）。
   - 其他平台将来各自映射到同一字段。
2. 订单列表/详情展示剩余时间，按紧迫度分档（如：已超时 / <24h / <3天 / 正常）。
3. 订单右栏与首页看板加"临近超时"提醒。
4. 可选：超时前 N 小时进异常中心（`ORDER_SHIPMENT_DEADLINE_NEAR`，见决策 6）。

**注意**：这是**平台事实字段**，不是 ERP 状态——不得与 `erpStatus` 混淆（AGENTS.md §38）。

## T2 货源信息（供应商可选 + 一次性采购说明）

**为什么**：实物来源的第一要素是"这批货从哪来"。但**不是所有采购都有供应商**。

**范围**：
- `suppliers` 表（编码 / 名称 / 联系人 / 电话 / 备注 / 状态）+ 标准 CRUD +
  零引用删除（沿用决策 0003 模式）。编码需新增一类业务前缀（如 `SUP%04d`），
  按 `master-data.md §1` 表格登记。**用于可复用的固定供应商**。
- `purchase_receipts` 增加两个**互不强制**的货源字段（见决策 1）：
  - `supplier_id`（可空）：固定供应商，建档案后可复用、可按供应商聚合做补货计划
  - `source_note`（可空，自由文本）：一次性网购，如"淘宝 订单号 12345678"

**UI 引导**：新建收货单时二选一——「选择供应商」或「填写货源说明」，
两者都留空时给提示但不阻断（避免录入摩擦）。

## T3 收货入库单（本 Sprint 核心）

### 数据模型

```text
purchase_receipts        收货单（表头）
  receipt_no             业务编号（集中式序号）
  supplier_id            供应商（可空，见决策 1）
  source_note            货源说明（可空，一次性网购用，见决策 1）
  purchase_order_id      采购单（可空，为 Sprint 9 预留，本期不实现）
  warehouse_id           收货仓库
  status                 DRAFT / RECEIVED / CANCELLED
  received_at            实际收货时间
  remark / created_by / created_at

purchase_receipt_items   收货单明细
  receipt_id / sku_id / quantity / unit_cost / bin_id / remark
```

**注意**：`supplier_id` 与 `source_note` 都**不是**「库存与实物关系」的载体——
建立该关系的是**收货单本身**（谁、何时、收了多少、入到哪个库位）。
两者只是货源信息，缺失不影响库存事实的成立。

### 状态机

```text
DRAFT ──确认收货──> RECEIVED（不可撤销，修正走库存调整）
  └──取消──> CANCELLED
```

### 关键约束

- **确认收货**才写库存：`PurchaseReceiptService.confirm()` → 逐行调
  `InventoryService.receiveStock()`。采购模块**绝不直接改 `inventory_balances`**
  （`工程架构文档:1005-1008` 明令）。
- 整单一个事务，任一行失败全部回滚。
- 重复确认幂等（`idempotencyKey = PURCHASE_RECEIPT:<receiptId>`）。
- `RECEIVED` 后不可改数量——库存已入账，改动必须走调整以保持流水可追溯。

### 界面

收货单列表（筛选：供应商/状态/日期/仓库）→ 新建（选供应商+仓库 → 加行：SKU+数量+成本+库位）
→ **确认前预览**（将入库哪些 SKU、各多少、入到哪个库位）。

## T4 端到端链路验证（本 Sprint 验收）

用户明确要求验证的链路，写成集成测试 + 手工验收脚本：

```text
1. 建立 Product + SKU（或复用 SKU000010001）
2. 建立平台映射（已有的「人工映射」入口）
3. 建收货单：供应商 X → 仓库 ZG-01 → SKU × N → 确认收货
       ↓ 断言 inventory_balances.on_hand = N
       ↓ 断言 inventory_transactions 有流水，reference = 该收货单
4. 订单进来 → 占用库存
       ↓ 断言 reservation RESERVED，available 减少，deadline 可见
5. 拣货 → 扫码
       ↓ 断言 Reserved → Picked
6. 发货
       ↓ 断言 On Hand 减少，订单行 SHIPPED
```

第 4–6 步代码已存在且有测试覆盖；本 Sprint 要验证的是**「入库产生的库存能被订单正常消费」**
这条衔接——特别是库存落在哪个库位、拣货扫码能否找到、可用量计算是否正确。

# 5. 需要用户决策的点

## 决策 1：供应商是否必填（已据用户业务澄清修正）

**用户业务形态**：大部分采购是**一次性网购**（接到订单后去网上买），卖家每次可能不同。
**因此原推荐（必填）作废。**

强制建供应商档案的后果：供应商主数据被几百个"只用一次的淘宝卖家"淹没，
真正要复用的固定供应商反而找不到；且每次收货都要先建档案，是纯粹的录入摩擦。

**修正后的方案**：

| 采购形态 | 记录方式 |
|---|---|
| 固定/反复合作的供应商 | 建 `suppliers` 档案，收货单引用 `supplier_id`；将来可据此做补货计划 |
| 一次性网购 | 只在 `source_note` 填一行（如"淘宝 订单号 12345678"），**不进主数据** |

- **A（推荐）**：两者都可空，UI 二选一引导，都空时提示但不阻断。
- **B**：二选一至少填一个（更严格的可追溯性，代价是每次收货多一步）。

推荐 A：`source_note` 近乎零摩擦，实际不会有人跳过；强制反而促使用户乱填。
若将来财务/审计要求可追溯，再收紧为 B 也不影响表结构。

## 决策 2：是否本 Sprint 就做采购单（PurchaseOrder）
- **A（推荐）**：不做。用户是"先售后采"，采购单在补货聚合（Sprint 9）前价值有限；
  一次做四张表属范围蔓延（AGENTS.md §74）。收货单预留 `purchase_order_id` 可空字段即可。
- **B**：一起做，范围明显变大。

## 决策 3：单位成本与移动加权平均
架构文档 §86 规定「采购成本采用移动加权平均，入库时更新成本」，而 `moving_average_cost`
字段注释写的就是"采购 Sprint 实现"——**本 Sprint 就是那个 Sprint**。
- **A（推荐）**：收货单记 `unit_cost`，确认收货时更新 `moving_average_cost`。
- **B**：本期只记 `unit_cost`，不计算平均成本（将来补算会缺历史数据）。

**注意**：选 A 会改变 SKU 成本语义，必须同步更新 `master-data.md` 与 `inventory.md`
（AGENTS.md §86 把 Cost 列为必须同步文档的业务）。

## 决策 4：新增库存引用类型
当前 `INVENTORY_REFERENCE_TYPES = ['MANUAL','TEST','ORDER','IMPORT']`
（`inventory/enums/inventory.constants.ts:76`）。收货入库需新增（如 `PURCHASE_RECEIPT`）
以便流水按来源对账。**枚举变更属业务规则**（AGENTS.md §98），需你确认。
不加的后果：收货流水与手工调整无法区分。

## 决策 5：平台库存"双轨期"是否接受
见 §4。推送能力就绪前，平台侧库存继续人工维护。
**需你明确知情并接受**：此期间系统库存与平台库存可能不一致，系统不会自动纠正。

## 决策 6：发货时限的预警方式
- 展示（列表/详情显示剩余时间）——**建议必做**
- 分档标识（已超时 / <24h / <3天）——建议必做
- 进异常中心（如 `ORDER_SHIPMENT_DEADLINE_NEAR`）——**需你确认**：
  这是新增异常类型（AGENTS.md §53 列表里没有），属业务规则变更。

## 决策 7：收货单归属哪个菜单
- **A（推荐）**：新建「采购」一级菜单（为 Sprint 9 采购单预留位置）。
- **B**：放在「库存」菜单下作为「收货入库」。
