# ADR 0024 — SKU 档案合并（重复档案归并）

日期：2026-10-24（用户拍板）
状态：已接受

## 背景

运营可能在不同平台商品上各自「快速建档」，导致**同一件实物**存在多个内部 SKU
（例如 Yandex 的一条变体和 WB 的一条变体各建了一个 SKU，本该是同一个 SKU 的两条
映射）。这类错误会同时污染库存、订单、采购与成本口径，必须有办法纠正。

## 决策

### D1. 合并 = 账面身份归并

同一件实物被记在两个 SKU 名下，所以合并不是「实物转移」，而是把两个身份重新
汇总成一条账：
- 现状数量（余额/占用/已拣/预留/序列号/安全库存）并到目标；
- **历史流水改指目标后按时间重放**，重算 before/after，保证「Σ流水 = 余额」
  且账链连续；
- 源 SKU 删除（所有引用都已迁走）。

### D2. 目标 SKU 的基础信息保留

名称、品牌、分类、型号、颜色尺寸、重量尺寸、成本一律以目标为准；源的同名字段
随删除丢弃（成本例外：目标为空时继承源的值）。操作员通过「输入目标 SKU 编码」
确认这次不可撤销的选择。

### D3. 冲突规则

| 数据 | 规则 |
|---|---|
| 条码 | 全局唯一：重复的源条码丢弃；主条码目标优先 |
| 图片 | 主图目标优先；源图并入为次图 |
| 安全库存 | 阈值不能相加：目标已有该仓则保留，否则继承源 |
| 序列号 | `serial_number` 撞号 = 同一实物记两次 → 拒绝合并 |
| 余额 | 同 `(仓,库位,SELLABLE)` 相加；不同维度改指；校验 `on_hand ≥ reserved+picked` |
| 流水 | 改指 + 重放；终值与余额不一致 → 拒绝合并 |

### D4. 架构与安全

- 库存写入只在库存模块内完成（`SkuMergeInventoryService`），符合 AGENTS §10；
- 其他模块的引用改指通过**进程内注册表**（各模块实现 `SkuReferenceRelink`），
  不跨模块 import 对方的表/Repository（AGENTS §9），也没有模块环；
- 单事务、按 SKU id 排序加锁、失败整体回滚；
- 写 `operation_logs`（`MERGE_SKU`）保留合并前后事实。

## 明确不做

- 不做批量合并（一次一对，逐个确认）；
- 不做「合并后撤销」：历史流水已并入目标，恢复源 SKU 需要重新建档并人工调整库存；
- 不在合并里自动重跑映射/分配：合并完成后按正常业务流程继续。

## 已知边界

- `inventory_transactions` 没有 condition 维度，因此合并只支持余额全部为
  `SELLABLE` 的 SKU（当前库内即如此）；出现其它状态时合并会拒绝，提示先扩展流水维度。
- 合并后的中间流水快照是「两条独立历史按时间交错后的合计」，不再是任一 SKU
  曾经的真实时点状态——这是把两个身份归并成一条账的必然结果。
