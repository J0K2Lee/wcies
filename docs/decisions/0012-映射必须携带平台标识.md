# 0012 映射必须携带平台标识；FAILED 订单行可重试解析

- **状态**：已接受（2026-09-11，用户报告订单映射失败后确认）

## 背景

用户手工创建了一张 Listing 映射（映射到 `SKU000010001`），随后平台订单同步进来却全部报 `ORDER_SKU_MAPPING_FAILED`。排查发现两处相互独立的问题。

### 问题一：映射可以不带任何平台标识

「新建 Listing 映射」表单允许 `platform_sku_id / seller_sku / offer_id` **三个全空**。这样的行能成功建立，但订单解析（`ListingResolverService.resolveInternalSku`）只按这三个标识反查，全空时直接抛 `NO_IDENTIFIER_PROVIDED`。

实测数据还原了时间线：

| 时间 | 事件 |
|---|---|
| 10:56:48 | 人工新建映射，三个平台标识全空 → 一条 MAPPED 但无标识的行 |
| 11:01:51 | Listing Sync 按 `(listing_id, platform_sku_id)` 去重，`4272776152` 不存在 → 又插一条 UNMAPPED 行 |

两条行**唯一键维度不同**（一条按 Listing 存在、一条按平台变体存在），永久并存且无法合并。订单带的是 `sku=4272776152` + `offer_id`，只能匹配到后者，而后者是 UNMAPPED → 映射失败。

**这条手工映射行从创建那一刻起就不可能被任何订单匹配到。**

### 问题二：FAILED 是终态，补映射后无路可走

`retryAllocation` 的前置校验要求 `mappingStatus === 'MAPPED'`，而映射失败的行是 `FAILED`；前端重试按钮的显示条件同样是 `MAPPED`。于是：

- 用户补好了映射 →
- 前端不显示重试按钮（条件写死 `MAPPED`）→
- 后端接口也拒绝（`ORDER_INVALID_STATE`）→
- **没有任何路径能让这一行重新解析**，订单永久停在 EXCEPTION。

## 决策

### 1. 手工映射必须至少有一个平台标识

创建变体映射时若三个标识全空，返回 422 `LISTING_SKU_MAPPING_IDENTIFIER_REQUIRED`，并在前端表单与弹窗顶部说明中引导。

判定顺序：**「同一 SKU 已映射到该 Listing」（409）优先于标识缺失（422）**——前者是更具体的诊断。

### 2. FAILED 行允许重试，且重试时重新解析

`retryAllocation` 拆成两条路径：

- `MAPPED + (BACKORDERED | PENDING)`：原有逻辑，直接分配库存。
- `FAILED`：调用新的 `retryFailedMappingItem()`，用**与摄入时相同的 store-scoped 规则重新解析**该行。解析成功则把行提升为 `MAPPED`、写入 `skuId`、**关闭 `ORDER_SKU_MAPPING_FAILED` 异常**，再走分配；解析仍失败则保持 FAILED 并回报解析错误码。

关键点：**不能信任行上存储的 `mappingStatus`/`skuId`**——人工可能已经修好了映射，存储的状态是过时证据。

### 3. 修复后仍缺货时必须落到 BACKORDERED

`allocateMappedItem()` 在库存不足时返回 `reserved:false` 但**不写** `fulfillmentStatus`——这对已经是 `BACKORDERED` 的行成立，但刚修复的 FAILED 行是 `PENDING`，会静默停在 PENDING 且没有库存异常。

因此重试路径在 `reserved:false` 时显式写入 `BACKORDERED` 并创建 `ORDER_OUT_OF_STOCK` 异常，然后重算订单汇总状态。

## 为什么不采用

- **只在 FAILED 时也允许重试、但不重新解析**：行的 `skuId` 是 NULL，无法分配。
- **放宽解析器接受 product_id**：`product_id` 是商品链接层级，一个链接下可有多个变体（本例即有 2 个），按它解析会引入猜测，违反冻结规则「严禁自动猜测映射」。已排除。
- **同步时按订单 offer_id 自动补建映射**：跨模块写 Listing 数据，改动面大；且订单到达时人工可能正在映射，存在竞态。留待后续按需评估。

## 影响

- `ORDER_SKU_MAPPING_FAILED` 从「终态」变为「可修复态」；异常在重试成功时自动 RESOLVED。
- 既存的「无标识映射行」不会被自动修复或删除（AGENTS.md §99），但可通过「人工映射」把正确标识补到同步行上，旧行保留为历史。
- 平台已同步的商品不应再用「新建映射」创建：Listing 已存在会因唯一键冲突失败。正确入口是该 Listing 详情里的「人工映射」。
