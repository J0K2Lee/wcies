# ADR 0020 — 移除商品（Product/SPU）层级，分类/品牌下沉 SKU

日期：2026-10-13（用户拍板，任务书《WCIES_改造任务书_移除商品层级_分类品牌下沉SKU_V1》）
状态：已接受（显式推翻 0002 的 SKU 派生编码、0014 的多变体挂靠、0008 中 `/products` 强删部分；0019 条码不受影响）

## 背景

系统长期存在 Product/SPU → Internal SKU 双层主数据：内部 SKU 才是库存/订单/
采购/成本/SN/调拨/售后的统一身份（AGENTS.md §23），Product 只承载"商品概念"
与分类/品牌档案，且 `sku_code` 派生自商品序号 + 商品内序号（决策 0002）。

实际使用中该层带来的是纯负担：

- 建 SKU 必须先建商品；Listing 快捷建档要在一个事务里建 Product + SKU，
  并衍生出"多变体挂靠同一商品/另建新商品"（决策 0014）等运营概念；
- SKU 导出的 Excel 需要 `product_code` / `product_name_zh` 两列；
- 商品页与 SKU 页的职责边界（分类/品牌挂在商品上）让"改一个 SKU 的分类"
  变成"改它所在商品的分类"，与运营直觉相反；
- SKU 编码形如 `SKU{6}{3}`，与商品序号强耦合。

用户 2026-10-13 拍板：**Internal SKU 是唯一商品主数据，分类/品牌是 SKU
字段**，删除商品层级。

## 决策（D1–D6）

1. **D1 删表（两阶段）**：阶段一 `20261013_001` 加列 + 回填 + `product_id`
   置空；阶段二 `20261013_002` 验证后 `DROP TABLE products` 并清死序列。
   两阶段之间 products 表保留供验证与回滚。
2. **D2 SKU 全局编码**：新编码 `SKU%09d`（最小宽度，溢出自然进位），单一
   `business_code_sequences` 作用域 `sku`；migration 回填序列起点 =
   存量 SKU 命名空间（`^SKU[0-9]+$`）数字后缀最大值 + 1，**存量编码冻结不
   迁移**。派生编码（决策 0002）与 `sku:{productId}` 作用域随之废止。
   防御：SKU 命名空间内出现非纯数字后缀的存量编码时报错中止（数字后缀
   最大值有歧义）；非 SKU 命名空间的手工编码（导入模板历来允许，如
   `VK87-BLK`）不在新编号空间内、无碰撞可能，冻结并计数。
3. **D3 快捷建档后 SKU = ACTIVE**：Product 的 `DRAFT`「档案未补全」语义整体
   废除、不迁移到 SKU；`POST /skus` 的默认状态维持现状（ACTIVE）。
4. **D4 补品牌管理 UI**：与分类管理弹窗同级、同交互模式（列表/改名/停用/
   删除），入口移到 SKU 管理页。后端 `/brands` CRUD 原已与 categories 齐平。
5. **D5 继承语义**：`category_id` / `brand_id` 成为 `skus` 列；每个 SKU 从原属
   Product 单射继承一份（回填 N:1 确定，无歧义），之后各 SKU 可独立修改。
   分类仍必须三级（决策 0005 不变）。
6. **D6 直接破坏式删除 `/products` API**：无兼容期，前端同步改；前端商品页、
   `/products` 路由与「商品管理」菜单项一并删除。

## 影响面

- 数据库：`skus` 加 `category_id`/`brand_id`（FK categories/brands + 索引）、
  `product_id` 置空；阶段二 drop `products` 与 `seq_product_code`。
- 后端：删除 product 控制器/服务/仓储/实体与 `PRODUCT_*` 错误码；
  `SkuService` 直建（无 productId）、分类/品牌校验、全局编码；
  catalog 删除保护改挂 SKU；listing 快捷建档事务内直建 SKU；
  SKU 导入模板删商品列、新增 `brand`/`category` 按名称精确匹配。
- 契约：`openapi.json` / `api-client` 再生成，`/products*` 与 `Product*` schema
  清零；`SkuResponseDto` 增 `categoryId/categoryName/brandId/brandName`。
- 前端：删商品页/路由/菜单；SKU 页成为主数据中枢（分类管理迁入 + 品牌管理
  新增）；建档链路全部对齐新契约。
- 文档：`master-data.md` §1/§2/§10/§12/§14 与 `AGENTS.md` 规则 23/24、
  `architecture/overview.md` ER 图同步改写。

## 不变量（改造不得触碰）

- integration 层平台侧 `product_id` / `description_category_id`（同名异物）；
- `platform_category_mappings` 表与其写入路径；
- 库存/订单/采购/调拨/财务的表结构（只依赖 SKU）；
- Listing 唯一键、映射状态机与解析语义。

## 附注：全局 SKU 序列的取值语义（2026-10-13 实施时确认）

`business_code_sequences.next_value` 在本项目中的语义是「**已发出的最大号**」
（取号 SQL 为 `INSERT … VALUES (scope, 1) ON CONFLICT DO UPDATE SET next_value =
next_value + 1 RETURNING next_value`，返回并存储的即新值）。因此：

- 迁移 `20261013_001` 把 `sku` 作用域播种为 `max(数字后缀) + 1` 时，**首个真正
  发出的编码是 `max + 2`**（保守跳过一个号）。这是安全的：全程单调、且必然
  大于全部冻结的存量编码（唯一性与单调性是本改造真正依赖的不变量，跳号不构成
  问题，D2 亦未禁止跳号）。
- 空库（无存量 SKU）时播种值为 1，首个编码为 `SKU000000002`。
- 已在 dev / 测试库应用的实例保持上述值不变；不为此追加「减 1」类补偿迁移
  （那会在已发号之后重新发出旧号，反而制造重复）。
- 若后续希望消除这一个跳号（仅影响全新环境），可把播种表达式改为
  `MAX(数字后缀)`（空库取 0），使首发 = `max + 1`；该调整须与新环境的验证一并
  进行，且需同步 T1 迁移测试中对 `next_value` 的断言。
