# 0001 集中式业务编码序号表

- **状态**：已接受（2026-09-11，Sprint 6 手工测试修复）
- **决策人**：用户（任务书第 3 节决策 #3–#10）

## 背景

Sprint 6 之前系统只有 3 条 PostgreSQL sequence（`seq_product_code`、`seq_sku_code`、`seq_internal_barcode`），仓库 / 店铺 / 品牌 / 分类的编码全部要求人工输入，导致编码格式混乱（用户手工测试问题：仓库 6、店铺 2、商品 1、商品 4）。

新编码规则要求序号按**作用域**递增：

- 仓库：按仓库类型各自递增（`ZG-01`、`SF-01` 各自独立）；
- 店铺：按平台各自递增（第一个 OZON 店 `ON-001`，第一个 WB 店 `WS-001`）；
- SKU：**按商品**各自递增（每个商品的第一个 SKU 都是 `001`）。

## 决策

建立一张集中式 `business_code_sequences` 表 + 统一的取号服务 `BusinessCodeService`：

```text
scope_key（作用域键，主键） + next_value（下一个可用序号）
```

作用域键约定：`warehouse:{TYPE}`、`store:{PLATFORM}`、`brand`、`category`、`product`、`sku:{productId}`。

取号用单条 SQL 完成（INSERT ... ON CONFLICT DO UPDATE ... RETURNING）。

## 理由

1. **为什么不用 PG sequence**：店铺编码需要"按平台各自递增"，SKU 编码需要"按商品各自递增"——这两个需求本质是**动态作用域序号**。平台数量固定尚可手工建序列，但商品数量不定，不可能为每个商品建一条 PG sequence。必须自上而下建"作用域序号"能力。
2. **原子性**：`INSERT ... ON CONFLICT (scope_key) DO UPDATE SET next_value = next_value + 1 RETURNING next_value` 是单条 SQL，PostgreSQL 保证原子性，不存在"读—改—写"窗口，无需应用层锁。
3. **并发正确性**：N 个并发请求取同一作用域，由行级锁串行化，必然得到 N 个互不重复的号。该性质必须由真实 PostgreSQL 集成测试锁住（并发取号不重号）。
4. **溢出语义**：宽度是最小宽度，序号溢出自然进位（`%02d` 对 100 输出 `100`），不报错、不截断。`String.padStart` 天然满足。
5. **bigint 驱动返回**：PG 驱动对 bigint 可能返回字符串，服务层必须显式 `Number(...)`。

## 影响

- 迁移：新增 `business_code_sequences` 表（不回填历史 sequence；商品编码切换时从旧 `seq_product_code` 的当前值之后继续）。
- 内部条码继续使用现有 `seq_internal_barcode`（决策 #9，保持 `WCSKU%08d` 不变），不走本表。
- 各业务模块通过 `BusinessCodeService` 公开方法取号，禁止直接读写该表（AGENTS.md §9）。
