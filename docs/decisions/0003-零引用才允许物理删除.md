# 0003 零引用才允许物理删除

- **状态**：已接受（2026-09-11，Sprint 6 手工测试修复）
- **决策人**：用户（任务书第 3 节决策 #2）

## 背景

用户手工测试发现仓库 / 店铺 / 店仓绑定 / 品牌分类 / 商品 SKU / 平台映射等主数据"无法删除"，建错了的数据只能留在系统里。而 `master-data.md:23` 原文是"Store/Warehouse/Binding/Listing 不提供硬 DELETE"，`:24` 又允许"无业务引用的 Barcode、SKU 图片、错误创建的数据物理删除"——例外条款一直存在，但代码里没有 DELETE 端点落地它。

## 决策

1. 为 Warehouse / WarehouseBin / Store / StoreWarehouseBinding / Brand / Category / Product / Sku / PlatformListing / ListingSku 十类实体增加 `DELETE` 端点。
2. **零引用才可删**：删除前在服务层逐一检查引用来源；存在任何引用 → 返回 `*_IN_USE` 错误码 + 提示"该记录已被引用，只能停用不能删除"；零引用 → 真删 + 记 operation log。
3. 子分类不是"引用"而是层级关系，单独使用 `CATEGORY_HAS_CHILDREN`。
4. `DELETE /listings/:listingId/skus/:id` 修复既有缺口：注释声称"无订单历史才可删"，但原实现无任何引用检查，有订单时撞 FK 报数据库级错误——补显式检查 `order_items.listing_sku_id` → `LISTING_SKU_MAPPING_IN_USE`。
5. Platform 保持只读，不提供删除。

## 理由

1. **与 `master-data.md:23` 的关系**：本决策是 `:24` 例外条款的代码落地，不是推翻 `:23`。"有引用 → 只能停用"的原则不变；变的只是"零引用的错误数据"从"删不掉"变成"可以删"。
2. **为什么必须在服务层预检**：所有 FK 均为 `NO ACTION`，硬删被引用行时数据库抛原始错误，用户看到通用数据库错误，无法知道原因。服务层预检把数据库错误转译为可读业务错误。
3. **与 AGENTS.md §25（业务数据可追溯）的一致性**：被业务流程引用过的数据（有订单 / 有库存流水 / 有库存余额）永远不删，可追溯性不受影响。允许删的只有"从未进入业务流程"的错误数据。
4. **Repository / Service 分工**：引用计数查询放 Repository，检查与抛错在 Service（AGENTS.md §8）。

## 影响

- 全部删除操作记录 `operation_logs`（`action: 'DELETE'`）。
- 错误码新增：`WAREHOUSE_IN_USE`、`BIN_IN_USE`、`STORE_IN_USE`、`BINDING_IN_USE`、`BRAND_IN_USE`、`CATEGORY_IN_USE`、`PRODUCT_IN_USE`、`SKU_IN_USE`、`LISTING_IN_USE`、`LISTING_SKU_MAPPING_IN_USE`。
- 前端详情抽屉增加"删除"按钮，被拒时展示后端返回的具体原因。
