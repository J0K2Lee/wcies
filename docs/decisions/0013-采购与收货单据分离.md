# 0013 采购单与收货单分离；订单行采购状态派生呈现

## 背景

用户的主营模式是「先售卖、再进货」：OZON 订单进来后，按订单去网上采购，货到后收进仓库再发给买家。该模式暴露三个系统缺口：

1. **入库缺失**：没有真实收货动作。`POST /inventory/receive` 只是库存原语，无业务单据、无供应商、无「这批货从哪来」的凭证。用「调整初始库存」代替收货无法建立库存与实物来源的关系（用户明确否决）。
2. **采购登记缺失**：`order_items` 没有任何采购字段，`BACKORDERED` 混淆了「还没采购 / 已采购在途 / 已到货待入库」三种需要不同处置的实况，导致重复采购或漏采购（用户点名风险）。
3. **时限不可见**：平台要求的发货截止时间（OZON `shipment_date`）只存在于 `raw_data`，界面看不到，「先售后采」无法与平台时限赛跑。

## 决策

### 1. 采购单（意图）与收货单（库存事实）是两张单据

- **采购单（Purchase Order）**：登记「已下单采购」的意图。可取消（未收货前），**不触碰库存**。
- **收货单（Purchase Receipt）**：不可逆的库存事实凭证。确认时才逐行调用 `InventoryService.receiveStock` 写库存与流水。

理由：两者生命周期不同（意图可撤回、事实不可撤回），合并会让一个状态机同时承担两种语义——与 Order / Shipment 分离（AGENTS.md §37）同理。嫌操作繁琐的问题用「从采购单生成收货单」一键预填解决，而不是合并单据。

### 2. 订单行采购状态「派生，不落库」

`order_items` **不新增采购字段**。订单行的采购状态由采购单明细实时派生：

| 派生状态 | 判定 |
|---|---|
| `NOT_ORDERED`（待采购） | 该订单行没有关联的**未取消**采购单明细 |
| `ORDERED`（已采购） | 有关联明细，且 `received_quantity < quantity` |
| `ARRIVED`（已到货） | 有关联明细，且 `received_quantity >= quantity` |

收益：状态永远与采购单事实一致，不存在「订单说已采、采购单说没采」的第二事实源（AGENTS.md §13）。派生服务由 purchase 模块提供只读查询，order 模块经端口组装响应（order 不得 import purchase 的 Repository，AGENTS.md §9）。

### 3. 供应商可空 + 货源说明可空（一次性网购不进主数据）

大部分采购是一次性网购（卖家每次不同）。强制建供应商档案会让主数据被一次性卖家淹没。规则：

- 固定供应商 → `suppliers` 主数据，采购单/收货单引用 `supplier_id`；
- 一次性网购 → `source_note` 自由文本一行（如「淘宝 订单号 12345678」）；
- 两者都可空；UI 二选一引导，全空提示但不阻断。

### 4. 防重复采购

为某订单行创建采购明细时，若该行已存在**未取消**的采购单明细，拒绝并返回 `PURCHASE_ORDER_ITEM_ALREADY_ORDERED`（409，消息含已有 PO 号与登记时间）。这是用户点名的核心风险，由后端强制。

### 5. 收货确认的原子性与幂等（随本决策一并确认的实现契约）

- 整单一个数据库事务：任一行失败全部回滚。库存写路径用 Inventory 模块的**事务感知 API**（`receiveStockInTx`，与 Sprint 4 `pickStockPartialInTx` 同一模式）——purchase 模块持有事务边界但不掌握库存计算。
- 幂等键 `PURCHASE_RECEIPT:<receiptId>:<receiptItemId>`；重复确认已 `RECEIVED` 的收货单返回幂等结果，不重复入账。
- `RECEIVED` 后不可改数量（库存已入账，修正走库存调整，保持流水可追溯）。
- 库存流水 `reference_type = 'PURCHASE_RECEIPT'`、`reference_id = <收货单ID>`（用户确认新增该引用类型）。

### 6. 移动加权平均成本随收货更新（用户确认）

架构文档 §86 规定「采购成本采用移动加权平均，入库时更新成本」，`skus.moving_average_cost` 即为此预留。收货单明细记 `unit_cost`（可空）；**确认收货时**更新：

```text
新平均成本 = (原平均成本 × 原在库数量 + 本次单位成本 × 本次数量) / (原在库数量 + 本次数量)
```

- 数量取该 SKU 全仓 `on_hand` 合计（含全部 Condition，货已在库）；
- 原平均成本为 NULL（无历史成本）时，以本次单位成本为新平均成本；
- `unit_cost` 为空的明细不参与成本更新；
- 未确认收货不改变成本；计算在确认事务内用数据库 NUMERIC 运算完成（禁 FLOAT，AGENTS.md §58）。

### 7. 发货时限是平台事实字段（用户确认进异常中心）

`orders.shipment_deadline`（TIMESTAMPTZ，可空）由平台映射器从容错解析提取（缺失/非法置 NULL，不阻断同步）；`raw_data` 原文保留（AGENTS.md §34）。它是平台事实，**不是 ERP 状态**（§38）。剩余时间分档：已超时 / <24h（紧急）/ <3 天（临近）/ 正常。摄入时若时限已近（<24h）或已超时且订单未发完，创建 `ORDER_SHIPMENT_DEADLINE_NEAR` 异常（新增异常类型，用户确认）。

### 8. 暂存用显式库位，不放宽 DEFAULT 规则（用户确认方案 A）

收货后逐渐上架的需求用**显式暂存库位**满足（如库区 `ST` 的库位）：收货进暂存位，之后用现有 `MOVE_BIN` 上架。不修改 `resolveDimension` 的「已有库位的仓库必须显式指定 binId」约束。
