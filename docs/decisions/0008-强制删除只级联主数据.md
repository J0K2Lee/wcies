# 0008 强制删除只级联主数据

- **状态**：已接受（2026-09-11，二次手工测试修复）
- **决策人**：用户（"只级联主数据"）

## 背景

决策 0003 落地了"零引用才可删"，但二次手工测试暴露出它的实际代价：商品下有 SKU 就删不掉，得先把每个 SKU 的条码、图片、平台映射逐个删干净，再删 SKU，最后才能删商品。用户实际关心的是"这个商品是我录错的，我要它彻底消失"，而不是"我要逐个清理子对象"。

用户提出的诉求原话是：删除商品时弹出确认窗口，勾选"强制删除"复选框后可以直接删除，同时删除关联的 SKU 及其映射；删除 SKU 时同理。

## 决策

1. 删除确认窗口统一为共享组件，带"强制删除"复选框；不勾选 = 决策 0003 的零引用语义，勾选 = 级联。
2. **强制删除只级联主数据**：
   - 商品 → 其 SKU、SKU 的条码 / 图片 / 平台映射 / 捆绑关系
   - SKU → 其条码 / 图片 / 平台映射 / 捆绑关系
   - 平台映射 → 仅映射行本身（Listing 记录保留）
3. **业务历史永远阻断删除，勾选强制也不行**：
   - `inventory_balances` / `inventory_safety_stocks` / `inventory_reservations` / `inventory_serials` / `inventory_transactions`
   - `order_items` / `picking_task_items` / `package_items` / `package_item_serials` / `shipment_items`
   - 命中时返回 `PRODUCT_HAS_BUSINESS_HISTORY` / `SKU_HAS_BUSINESS_HISTORY`，消息中列出具体表名与行数，并提示"改用停用"。
4. API 用 `DELETE /products/:id?force=true`、`DELETE /skus/:id?force=true` 表达；不带 `force` 时行为与 0003 完全一致。
5. 级联在整个事务中完成（先清子表，再删主体）；审计记录 `action: 'FORCE_DELETE'`，并记录被级联的 SKU 数量。

## 理由

1. **主数据与业务历史是两类东西**。条码、图片、映射、捆绑关系是"可重建的描述"，删掉只损失重新录入的时间；库存流水、订单行、拣货/发货记录是"发生过的物理事实"，删掉就再也无法回答"这批货去哪了"。把二者分开，才能既满足"录错了要能清掉"又不破坏 AGENTS.md §25 的可追溯性。
2. **不与决策 0003 冲突**。0003 保护的是"已被业务引用的数据"，0008 放开的是"引用它的只有描述性主数据"这一情形。两者是同一条原则（引用决定可否删）在两层的具体化。
3. **为什么不能连库存一起删**。库存表是库存核心的账本；从主数据删除路径去删账本行，等于绕过 `InventoryService` 修改库存（AGENTS.md §10 明令禁止），且会让 `InventoryTransaction` 与余额对不上（§14：任何库存变动必须有流水，流水不可凭空消失）。
4. **为什么强制删除仍要报具体表名**。用户勾了"强制删除"却被拒绝，若只回一句"不能删除"会被认为是 bug 而反复重试；报出 `inventory_transactions(3)` 能让他立刻理解"这东西真的动过货"。
5. **为什么 Listing 记录要保留**。平台链接是平台侧的客观存在，删掉本地记录只会让下次同步重新拉回来（并可能触发"unmapped"告警）。只断开 SKU 映射更符合事实。

## 影响

- 新增错误码 `PRODUCT_HAS_BUSINESS_HISTORY`、`SKU_HAS_BUSINESS_HISTORY`。
- 新增共享前端组件 `DeleteConfirmModal`（含强制复选框与警示文案），商品 / SKU / 映射 / 凭证统一使用。
- 级联表清单与"匹配列"集中定义在 `apps/api/src/modules/product/constants/sku-delete.constants.ts`，供 Repository 与 Service 共用一份描述。
- 集成测试 `tests/integration/force-delete.integration.spec.ts` 覆盖：无流水时级联成功、有库存流水时拒绝且不删任何行、审计记录、普通删除不隐式级联、SKU 强制删除断开映射但保留 Listing。
- 凭证删除（`platform_credentials`）不适用本决策：它没有任何引用方（订单/库存引用的是店铺而非凭证），错误录入的密钥可直接删除后重录。
