# 0018 订单发货流程：定向解除 Read-first，加入平台组包与面单

- 状态：已采纳
- 日期：2026-09-18
- 相关：AGENTS.md §22/§25/§37/§86/§88/§92/§95/§97、decision 0016、`docs/business-rules/orders.md` §3/§15A/§15C、`docs/integrations/ozon.md` §9c

## 背景

系统此前的订单履约是**纯内部**的：拣货 → 建发货单 → 建包裹 → 扫码装箱 → 封箱 → 正式出库，
全程不通知平台（`PlatformAdapter` 契约只有读方法，头注释明确写了
「Write operations (push inventory, prices, shipments) are intentionally NOT part of this contract yet」）。

用户指出的真实日常流程不同：

```text
获取运单号（订单管理页一键，并显示）→ 拣货 → 发货（点击发货按钮，通知平台）
```

现状差距有三处：**完全没有运单号获取能力**（OZON 的 `tracking_number` 只躺在 `raw_data` 里，
mapper 从不读它）、**发货必须去仓库作业页走五步**、**全程不通知平台**。

## 决策

### 1. Read-first 边界定向解除——只开两个能力

契约新增**可选**方法（`packages/platform-contracts`）：

```ts
prepareShipment?(context, { platformOrderId }): Promise<PlatformShipmentPreparation>
fetchShippingLabel?(context, { platformOrderId }): Promise<PlatformLabelFile | null>
```

- 只开这两个。库存推送、价格、促销、退货动作等**仍然不做**。
- 方法是**可选**的：未实现即「该平台不支持」，调用方抛
  `PLATFORM_CAPABILITY_UNSUPPORTED`，**不得回退猜测**（§88）。
- 后端把能力位放进订单详情 DTO，前端据此显隐按钮——前端不判断平台名，
  新增平台零前端改动。

### 2. 「获取运单号」= 平台组包，且是**唯一**的平台写

OZON 的组包（`POST /v4/posting/fbs/ship`）就是平台侧「已发货」那一步
（`awaiting_packaging` → `awaiting_deliver`），规范中其后再无面向卖家的状态写接口，
因此「发货」不重复写平台（用户 2026-09-18 确认「一次组包就够」）。

**实测反证了「先取号再组包」的直觉**：本地库 197 单中，
`awaiting_deliver`/`delivering` 的 155 单**全部**有 `tracking_number`，
16 单 `awaiting_packaging` **全部没有**。
→ 平台只在组包时分配运单号，「获取运单号」必须先组包。业务需求与接口事实一致。

组包必须**回读确认**（规范明确 200 不代表成功），未确认时抛错而非当成功——
宁可让操作人重试，也不掩盖「平台没受理」。

### 3. 一键出库是既有阶梯的**编排**，不是新阶梯

`QuickShipService` 依次调用既有的公开服务：
建发货单（仅 PICKED 行）→ 开箱/装箱/封箱 → `shipShipment`。

- **不绕过任何打包规则**：`ensureOpenPackage` 与 `packAllItems` 保留
  `scanItem` 的全部不变量（发货单行锁、不超量、SN 必须来自本订单已拣货序列号），
  只把「逐件扫码」换成「取快照仍欠的数量」。打包依旧不动库存。
- **库存仍只有 `shipStockPartialInTx` 一个扣减入口**，流水一条不少。
- 手工多包裹精细装箱能力**保留**，两者互不排斥。
- 用户明确表示仓库作业不需要多包裹精细装箱，因此一键路径固定单包裹——这是
  **新增一条快捷路径**，不是删除既有能力（§95/§99）。

### 4. 并发：按订单加 advisory lock

一键发货跨多个事务（建单 / 装箱 / 封箱 / 出库），**单行锁覆盖不了**，
两个并发请求会各自建发货单并撞上
`uq_shipment_items_order_item_active` 唯一索引 → 500。
**实测发现**（并发集成测试），因此按订单加 PostgreSQL advisory lock 串行化，
并把「该不该开箱 + 开箱」放进发货单行锁内（空箱永远无法封箱，会让发货单卡死在 PACKING）。

AGENTS.md §18 允许「PostgreSQL 行级锁**或经过明确验证的等效并发控制**」，
advisory lock 属于后者，且由集成测试证明：并发两次发货只扣一件库存。

### 5. 运单号落位 `orders.platform_tracking_no`，不违反 §3 禁令

`orders.md` §3 禁止的是把 `orders.tracking_number` / `orders.package_id` **当作物流模型**。
新列是**平台事实**（与 `platform_status` / `platform_stage` 同类）：只读展示 +
出库时填入 `shipments.tracking_number`。内部物流载体仍然只有 Shipment / Package。

### 6. 面单在 `shipping_labels` 上加 `order_id`

平台面单在组包后即可取，那时**还没有内部 Shipment**（发货单只能由 PICKED 行创建）。
选择给既有表加 `order_id`（`shipment_id` 改可空 + CHECK 至少其一非空），
而不是新建平行面单表（§85/§99）。`source = PLATFORM_API` 是 Sprint 4 预留值的正式启用。

### 7. 失败分级：只有真实平台故障进异常中心

`ORDER_PLATFORM_SHIP_FAILED` 只在 **5xx 类失败**（平台/基础设施故障，或受理但未确认组包）
时创建；4xx 前置条件（平台状态不允许、组包进行中、平台未接入）**不建异常**——
操作人当场看到原因，重复点击不应淹没异常中心。成功组包自动解除。

## 后果

- 系统首次具备真实平台写能力，因此：写操作只在显式用户操作下发生、带确认弹窗、
  测试一律脚本化传输（`OzonClientFactory` 拒绝回退真实 URL），真实调用需用户授权（§92）。
- 本次交付的 OZON 两个端点**尚未对真实账号执行**，T0 清单见
  `docs/integrations/ozon.md` §9c。
- WB / Yandex 未实现（仓库内无经核实的发货写接口事实：WB supplies-api 已被平台停用，
  Yandex 无 `status/update` 类文档）。契约与前端能力位已就位，
  拿到官方文档后按同一模式补齐，不动订单核心。

## 备选方案与否决理由

- **在 OrderService 里直接写平台调用**：违反 §32/§33 与架构 Rule 5（平台端点只能出现在
  `modules/integration/`），已否决。
- **新建独立履约模块**：本次只有 4 个订单级动作、且 2 个是平台调用，
  新增顶层模块的收益不抵结构成本；改为沿用 `PlatformWarehouseController` 先例，
  把编排放在 sync 层、把内部出库编排放在 Shipment 模块的公开 Service（§7）。
- **把组包放在「发货」按钮里、取消「获取运单号」**：与用户真实流程不符
  （他们要先拿运单号去贴单/打印），且组包失败时会导致拣完货才发现发不出去。
