# 0005 三级分类语义

- **状态**：已接受（2026-09-11，Sprint 6 手工测试修复）
- **决策人**：用户（任务书第 3 节决策 #6、#12、#13、#14）

## 背景

原分类表只有 `parent_id` 自引用，无层级限制、无重名校验、前端级联只展开两层，三级类目根本选不到；商品挂分类也不校验层级。用户手工测试明确要求"最多三级、商品只挂三级、同父下重名拦截、补分类管理视图"。

## 决策

1. **最多三级**：`categories.level ∈ {1,2,3}`，由数据库 CHECK 兜底；根节点 `level = 1`（CHECK 保证 `(level = 1) = (parent_id IS NULL)`）。
2. **商品只挂三级**：商品分类**选填**，填则该分类 `level` 必须 = 3（错误码 `CATEGORY_LEVEL_INVALID`）。
3. **同父下名称唯一**：唯一索引 `(parent_id, lower(name_zh)) NULLS NOT DISTINCT`——`NULLS NOT DISTINCT` 保证根级之间（`parent_id` 均为 NULL）的重名也被拦截；错误码 `CATEGORY_NAME_DUPLICATED`。
4. **编码**：一/二/三级共用一条序列 `CN%05d`，编码不出现在前端表单。
5. **改父规则**：创建/改父时计算**整棵子树的最终深度**，超过三级拒绝（`CATEGORY_DEPTH_EXCEEDED`）；已有商品的节点移动后不再是三级 → 拒绝（`CATEGORY_LEVEL_INVALID`）。`level` 在改父时整棵子树同事务更新。
6. **停用不级联**：停用节点及其子树在商品表单不可选，但数据库层级与商品挂载关系不变；重新启用即恢复。
7. **删除**：有子节点 → `CATEGORY_HAS_CHILDREN`；有商品 → `CATEGORY_IN_USE`；零引用 → 真删。
8. **商品筛选含子树**：`GET /products?categoryId=` 从精确匹配改为递归 CTE 含全部子孙，否则一/二级分类只是展示层级。

## 理由

1. **level + CHECK 而非纯应用层校验**："最多三级"是业务铁律，由数据库兜底后任何代码路径（包括未来的导入脚本、后台脚本）都无法绕过。
2. **整棵子树高度校验**：只看被移动节点本身会漏判——带 3 层子树的节点挂到另一个一级下，子树高度 3 + 新父 1 = 4，越级。这是最容易实现错误的点，必须有测试锁住。
3. **`NULLS NOT DISTINCT`**：PG 默认认为每个 NULL 互不相同，不加此限定，根级分类之间的重名不会撞唯一索引。
4. **跨父允许同名**：唯一性作用域是"同父"，不同父下允许同名（`数码/线材` 与 `家装/线材` 并存合理）。
5. **商品只挂三级**：分类的实际运营用途是归集到最细粒度；挂一/二级会让"含子树筛选"失去确定性语义。

## 影响

- 迁移：新增 `level` 列（递归回填后 NOT NULL + 两条 CHECK）+ 同父名称唯一索引。
- 服务层新增错误码：`CATEGORY_DEPTH_EXCEEDED`、`CATEGORY_LEVEL_INVALID`、`CATEGORY_NAME_DUPLICATED`、`CATEGORY_HAS_CHILDREN`、`CATEGORY_IN_USE`。
- 前端：商品表单分类改 `Cascader`（只能选三级）；分类管理视图（编辑/停用/启用/零引用删除/同级排序/改父）。
