# 0010 库位编码即条码：单一字符串，含仓库前缀

- **状态**：已接受（2026-09-11，库位批量创建修复）
- **决策人**：用户（"库位编码按照条码逻辑存，信息更丰富，能确定到仓库"）

## 背景

原始实现里库位有**两个不同的字符串**：

| 字段 | 写入规则 | 谁在用 |
|---|---|---|
| `bin_code` | 批量接口 `{仓库编码}-{货架}-{层}`；单建接口由用户手填 | 界面表格；**扫码解析**（拣货 / 拦截 / 导入） |
| `barcode` | 批量接口 `BIN-{bin_code}`；单建接口 `BIN-{仓库编码}-{用户手填}` | 仅库位列表的关键词搜索 |

问题有三层：

1. **两个接口生成的规则本身不一致**：单建时若用户按批量格式填 `ZG-01-A01-01`，条码变成 `BIN-ZG-01-ZG-01-A01-01`，仓库编码出现两次。
2. **扫码只认 `bin_code`**：`findByWarehouseAndCode()` 全程按 `bin_code` 匹配，`barcode` 列不参与任何解析。因此若按字面把 `BIN-...` 值印成标签，扫码枪读回来的字符串在库里查不到——**印出来的标签会扫不动**。
3. `bin_code` **写入后不可修改**（`UpdateBinRequestDto` 不含该字段），且库位一旦有库存流水引用就不能删除。格式定错等于要重印全部货架标签。

## 决策

1. **一个字符串**：`barcode` 与 `bin_code` 存同一个值。标签印编码本身，扫出来的字符串必然命中。
2. **编码含仓库前缀**：格式为 `{仓库编码}-{货架}-{层}[-{位}]`，如 `ZG-01-A05-1`。理由：`warehouse_bins` 唯一键只是 `warehouse_id + bin_code`，不同仓库允许同名编码；带上仓库前缀后，标签离开系统上下文（贴在货架上、被拍照、被导出）时仍能辨认归属。
3. **货架号至少补零两位**，层号不补零：`A01-1` 而非 `A1-1`。库存分配与拣货按 `bin_code` 字典序排序（`reservation.service.ts` 的确定性加锁顺序、`inventory-balance.repository.ts` 的 `ORDER BY bin.bin_code`），补零使字典序等于实地行走顺序；否则 `A10` 会排在 `A2` 之前，拣货路径错乱。层号补零无此收益（层数少且不影响路径），故不补，保持标签简短。
4. **由服务端生成编码**，调用方只给布局意图（库区、起始货架号、货架数量、每架层数）。前端保留一份同规则预览函数用于弹窗提示，但**格式的事实源在后端**——前端预览只是展示，不参与写入。

## 为什么不采用

- **编码不含仓库前缀（`A05-1`）**：标签更短，但脱离系统上下文后无法判断属于哪个仓。用户明确要求"能确定到仓库"。
- **保留 `BIN-` 前缀作为条码值**：与前缀重复问题同源，且会让"编码"和"条码"再次分叉，重现第 2 条缺陷。
- **后端同时接受编码与条码两种字符串**（先查编码、再查条码列）：兼容旧标签，但等于长期维护两套字符串，迟早有人印错。已排除。

## 影响

- `barcode` 列保留（不删，AGENTS.md §99），语义改为"编码的印刷载体"，仅作关键词搜索与将来标签打印的数据源。
- 标签印刷规格必须用 **Code128 或二维码**（决策 0007 已选 Code128）：编码含字母与连字符，非纯数字，不能用 EAN-13。
- 历史库位（如 `TEST-A01`、`DEFAULT`）保留原值，不回溯改写；`DEFAULT` 是本系统为无实体库位管理的仓生成的虚拟库位，`ensureDefaultBin()` 仍按固定字符串创建，不走编码规则。
- 单建接口的 `binCode` 由必填改为选填：留空时按 区/架/层/位 自动生成，与批量规则一致；仍允许显式传入以兼容导入与手工特例。

## 后续修正

本文只解决了「一个字符串、含仓库前缀」；**货架段本身如何在两条创建路径间保持一致**由决策 0011 补齐（库区 + 货架号 → 货架，服务端统一组合）。010 的「区/架/层/位 自动生成」在 011 中被收紧为「区 + 货架号（数字）+ 层 + 位」。
