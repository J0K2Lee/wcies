# ADR 0022 — 加急订单与库存分配优先级（平台 > 发货时限）

日期：2026-10-16（用户拍板，订单优先级机制）
状态：已接受

## 背景

运营需要处理「某些特殊订单」，要求它们：

1. **优先展示**——在订单列表中一眼可见、排在最前；
2. **优先分配库存**——某 SKU 到货后，优先占用给这些订单。

同时用户明确了库存分配的优先级口径：**加急 > 平台 > 发货时限**，其中平台之间的
优先级由用户自行设置。

现状（实施前）：缺货到货的自动重分配由
`OrderAutoReallocationService.reallocateFor` 驱动，候选行来自
`OrderItemRepository.findUnallocatedItemIdsBySku(skuId)`，排序只有
`ORDER BY i.created_at ASC`（纯 FIFO，入库时间）。列表排序是白名单
`ORDER_LIST_SORT_FIELDS` + 纯函数 `orderSortOf()`，没有任何优先级维度。
平台表 `platforms` 已是订单列表查询的 JOIN 目标（经 `stores.platform_id`），
但没有优先级字段；系统也没有通用设置表。

## 决策

### D1. 加急是订单的业务标注，不是 ERP 状态

`orders.is_urgent boolean NOT NULL DEFAULT false` +
`orders.urgent_marked_at timestamptz NULL`（审计，记录最近一次标记加急的时间；
取消加急保留最后标记时间）。

加急**不进 `erp_status`、不写状态历史、不参与状态机**（AGENTS.md §38）——它只
影响两件事：订单列表置顶、缺货到货后的分配排序。写入走 `operation_logs`
（`MARK_URGENT` / `UNMARK_URGENT`，AGENTS.md §39 可追溯）。

**终态限制**：`SHIPPED` / `CANCELLED` 订单不可加急（对已完结订单无意义，且它们
不再参与分配）。`OrderService.setUrgent` 拒绝并返回 `ORDER_INVALID_STATE`；前端
旗标在终态订单上置灰不可点。已在目标状态时幂等返回，不重复写日志。

入口（用户指示：**只做行内旗标切换**，不做批量浮岛、不做右栏按钮）：
订单列表「订单号」列的旗标图标，单击即切换——**红色旗标 = 加急（附「加急」红色
徽标），黑白旗标 = 普通**。轻量、可逆、无平台副作用，属 L1 即时操作，不二次确认。

### D2. 平台分配优先级存于 `platforms.priority`

`platforms.priority integer NOT NULL DEFAULT 100`（数值小=优先，与
`warehouse_platform_bindings.priority` 同向）。种子三平台同值 100，用户再排。

理由：`platforms` 本就是订单列表查询的 JOIN 目标，分配排序零额外成本；语义正确
（平台之间，而非按店铺）；可在管理端直接编辑。备选（新建通用设置表 / 塞
`stores.settings`）均因「为单功能引入新表」或「语义错位」被否。

写入：`PATCH /api/v1/platforms/:id/priority`（`AdminGuard`），记 `operation_logs`。
前端在系统管理页「平台参数」卡片内联编辑（管理员），其他人只读。

### D3. 分配排序：加急 > 平台 > 发货时限 > 入库时间

`findUnallocatedItemIdsBySku(skuId, warehouseId)` 的顺序键：

```sql
ORDER BY o.is_urgent DESC,                       -- 1 加急
         p.priority ASC,                         -- 2 平台优先级（小=优先）
         o.shipment_deadline ASC NULLS LAST,     -- 3 发货时限（早者优先）
         i.created_at ASC                        -- 4 兜底（FIFO 稳定）
```

**加急不抢占**：加急只影响「新分配」的排序——加急缺货行排到候选最前，到货那一刻
优先拿到；但**不主动释放/夺取**已经 RESERVED 给其他订单的库存。这是 v1 的刻意
边界：抢占需要「释放 + 重占 + 幂等 + 释放方回退缺货 + 异常可见」一整条链路，
风险显著更高，未列入本次范围。

### D4. 候选行按「事件仓库」过滤（半连接）

候选查询新增：

```sql
AND EXISTS (
  SELECT 1 FROM warehouse_platform_bindings b
   WHERE b.store_id = o.store_id
     AND b.warehouse_id = $2::uuid   -- 事件仓库（货实际进了哪个仓）
     AND b.status = 'ACTIVE'
)
```

语义：**只有一个仓的到货，才让「被该仓服务的店铺」的缺货行参与竞争**——其余订单
在别的仓收多少货都轮不到它。这是仓库作业的现实直觉。

安全性：该过滤只**收窄**候选，从不新增；实际占用仍走店铺默认仓
（`resolveDefaultWarehouseId`），因此不会把货占错仓。它把
`StockIncreasedEvent.warehouseId` 从「仅用于并发闸键」升级为真正的业务维度。

注意：`order_items.warehouse_id` 在缺货行上**恒为 NULL**（建单不写、只有占用成功
/ 重试路径才写），所以过滤**不能**用行上的仓库列——必须用店铺绑定半连接。

### D5. 列表加急恒定置顶

`orderSortOf()` 无论用户选哪种排序，首级键恒为 `o.isUrgent DESC`——加急订单永远
排在非加急之前，组内再按用户所选键排。这是「优先展示」的语义，不是可选项。
前端不新增「加急排序」按钮（置顶是恒定的，不是一种可切换排序）。

## 后果

- `orders` / `platforms` 各加一列，配 `AddOrderUrgentAndPlatformPriority` 迁移；
  补 `warehouse_platform_bindings (store_id, warehouse_id)` 复合索引支撑 D4 半连接。
- 加急是纯粹的人工标注，不影响任何状态机、不产生库存流水、不改变平台事实。
- 分配优先级从单一 FIFO 变为四级键；仓库过滤让「其他仓到货误触发本行重分配」的
  无效尝试与误导性日志消失。
- 未做：抢占式重分配、按事件仓库直接分配（而非店铺默认仓）、拣货队列的加急排序。
  这些是后续可扩展点，需要时单独立项。
