# ADR 0014 — 快捷建档增强：多变体挂靠 + FOR UPDATE 并发 + 异步图片

日期：2026-09-14（Sprint 8.5，grilling 会话决策定稿）
状态：已接受

## 背景

Sprint 8 T1 的快捷建档（`POST /listings/:listingId/skus/:mappingId/onboard`）把「建 Product → 建 SKU → 可选条码 → 映射」压缩为一个事务，但存在三个已确认缺口（Sprint 8.5 规划 §1.2）：

1. **多变体裂变**：每个变体建档都新建独立 Product，一条 5 变体 listing 建完出现 5 个互不相关的 Product，违背 SPU 语义（AGENTS §23）。
2. **并发 TOCTOU 窗口**：UNMAPPED 预检在事务外、事务内 re-check 是普通 SELECT、`platform_listing_skus` 无唯一约束兜底——双请求可各建一套主数据，留下无映射孤儿。
3. **无图片**：v3 info 的 `primary_image`/`color_image` 已随 `raw_data` 入库但从未使用。

## 决策

1. **挂靠语义**：同 Listing 后续变体默认挂到该 Listing 首个已建档变体的 Product 下（SKU 编码按 `nextSkuCode` 顺延，无新编码规则）；弹窗提供显式「另建新商品」（`createNewProduct: true`）与指定挂靠（`existingProductId`）。挂靠时不改动已有 Product 的品牌/分类。
2. **并发**：onboard 事务**开头**对 mapping 行 `SELECT … FOR UPDATE`，串行化「检查 → 建档 → 映射」全程；重复提交语义**保持 409** `LISTING_SKU_MAPPING_INVALID_STATE`（不做幂等成功），并发双请求仅一成功、零主数据孤儿。
3. **映射基数**：允许多平台变体 → 同一 Internal SKU（人工映射路径），不拦截不加约束。
4. **DRAFT 语义**：建档 Product 停留 DRAFT 仅作「档案未补全」标记，不阻断任何业务。
5. **图片异步转存**：提交成功后入 BullMQ（`wcies.media`），下载 `color_image ?? primary_image` → `SkuImageService.upload()`（私有桶）→ 首图主图 → 首次回填 `products.main_image_id`（仅当为空）；失败自动重试，不进建档事务。
6. **品牌/尺寸重量**：品牌人工 Select + 快建（不自动提取）；尺寸/重量按 v4 enrichment 预填、可编辑，沿用全有或全无与体积后端计算规则。

## 后果

- 建档弹窗信息密度提高，以 `GET /listings/:id/onboard-context` 单端点供数。
- 「保存并下一变体」纯前端实现：商品锁定挂靠、类目/品牌/条码开关沿用。
- 集成测试必须覆盖：并发双 onboard 仅一成功、多变体 1 Product + N SKU。
