# 2. 下一阶段的核心判断

## 2.1 链路已通，入口太窄

把「一个新商品从订单到发货」的完整路径与现有能力对照：

| 环节 | 现有能力 | 状态 |
|---|---|---|
| 订单进来，listing 未映射 | `ORDER_SKU_MAPPING_FAILED` 异常 + FAILED 行可重解析（`880b0b7`） | ✅ |
| **建 Product + SKU** | 单条界面 / Excel 导入 | ⚠️ 单条慢，Excel 需离线填表 |
| **生成内部条码 + 打印标签** | ✅ Sprint 7 T6 | ✅ |
| **Listing 映射** | 人工映射（要求 SKU 已存在）/ Excel 导入 | ⚠️ 同上 |
| 重试解析/分配 → BACKORDERED | ✅ | ✅ |
| 登记采购（防重复） | ✅ Sprint 7 | ✅ |
| 扫码收货（含当场补码） | ✅ Sprint 7 | ✅ |
| 重试分配 → 拣货 → 发货 | ✅ Sprint 3/4 | ✅ |

**结论：Sprint 7 补完了中后段（采购→收货→库存），Sprint 8 要补的是前段入口
（建档→条码→映射）的效率。**两段接上，「先售后采」才对一个**新**商品全程无断点。

## 2.2 为什么现在做（而不是继续往后推）

1. **用户已开始真实收货**（§1.2），下一个动作必然是第二、第三个商品——
   每个都要付一遍五步手工成本。
2. **双轨期风险在累积**（前一版规划决策 5）：每多一个在管 SKU，系统库存与
   平台人工库存的不一致窗口就多一份。渠道推送（Sprint 10）的前置是
   「足够的库存数据」，而库存数据的入口就是建档+映射。**Sprint 8 不做，
   Sprint 10 就无从谈起。**
3. 前一版规划对 Sprint 8 的定位（§4 路线表）正是：*商品/SKU 批量建档 +
   映射批量补齐，前置依赖「Sprint 7 验证过单条链路」*——该依赖已满足。

## 2.3 两种形态都要，但优先级不同

| 形态 | 适用 | 判断 |
|---|---|---|
| **A. 界面快捷建档**（从 Listing 行一键「建档并映射」） | 日常主路径：货到了/订单来了，当场建一个 | **优先做**。用户的节奏是逐个商品处理，不是一次批 500 个 |
| **B. Excel 批量闭环**（导出未映射清单 → 补填 → 导回） | 一次性补历史存量、批量备货 | 导入端已有，只缺**导出**；做导出即闭环，成本低 |

理由：D2（只管有货的商品）决定了单日新增建档量是个位数到几十，界面快捷路径
是高频动作；1323 条存量里用户真正会管的也只是子集，Excel 闭环用来一次性收割。

# 3. Sprint 8 建议范围

## T1 从 Listing 快速建档（核心）

**目标**：把「建 Product → 建 SKU →（可选）生成内部条码 → 映射 Listing」
压缩成**未映射 Listing 行上的一个动作**。

要点：

1. 入口：Listing 页未映射行 → 「建档并映射」。
2. 预填：商品名/SKU 名默认取 `listing.title`（`platform-listing.entity.ts:31`），
   用户可改；编码沿用集中式序号（`business-code.service.ts` 的
   `nextProductCode()` / `nextSkuCode()`，**不新增编码规则**）。
3. 可选项：勾选「生成内部条码」（复用 `generateInternal`），成功后直接给
   打印入口（复用 Sprint 7 T6 打印页，不新做打印）。
4. **事务边界**：Product 创建（product 模块）+ SKU 创建（product 模块）+
   映射（listing 模块）跨两个模块，必须由一个应用层编排服务在一个数据库
   事务内完成，各模块通过公开 Service 参与（§7/§9；禁止 listing 直接
   import product 的 Repository）。**事务如何跨模块传递是本任务的主要设计点**，
   任务书中必须明确。
5. 失败语义：任一步失败整体回滚，不留「SKU 建了但没映射」的半成品。
6. 建档即映射**只允许从未映射行发起**；已映射行不提供（防误覆盖既有映射）。

## T2 未映射清单导出（Excel 批量闭环的另一半）

**目标**：让既有 LISTING_MAPPING 导入形成「导出 → 补填 → 导回」闭环。

1. 导出内容与导入模板**逐列对齐**（§1.3 模板），`internal_sku_code` 列留空，
   用户补填；已映射的行默认不导出（可选用筛选控制）。
2. 导出走后台生成 + 对象存储签名 URL 下载（复用 ImportJob/文件通道的既有
   模式；大文件生成属长任务则进 BullMQ，§50）。
3. 幂等与防重沿用导入端既有行为（相同映射拒绝、决策 0012 平台标识校验），
   **不新发明规则**。
4. 配套：SKU 批量导入模板的下载入口在导入页补齐（如已有则验证即可），
   形成「先导 SKU、再导映射」的两步指引文案。

## T3 未映射工作台体验（轻量）

在既有 Listing 页「待映射」筛选（`ListingsPage.tsx:399`）之上：

1. 列表页顶部显示未映射总数（1323 这类数字直接可见，回答「还剩多少没管」）。
2. 「有订单撞上来的未映射」优先级置顶：被 `ORDER_SKU_MAPPING_FAILED` 异常
   引用的 listing 排前（数据已有——异常表引用 order/order_item，订单行有
   listing 映射状态），让用户先处理真正造成异常的那些，而不是按同步顺序翻页。
3. 不新增业务状态、不做「忽略/归档」标记（§6）。

## T4 携带决策的落地（待第 5 节确认后纳入）

### T4a 移动加权平均成本（原 Q2）

**建议本 Sprint 做**，理由：

- 架构文档 §86 本来就规定「入库时更新成本」，字段注释写的也是
  「采购 Sprint 实现」；
- **数据安全警告**：`unit_cost` 是可空的——如果收货时不填，这段历史的成本
  就**永久缺失**，将来无法回填（货源报价单不会留在系统里）。做得越晚，
  缺口越大。用户现在已开始真实收货（§1.2），每张收货单都在产生历史。

实现要点：确认收货事务内，按
`(原成本×原数量 + 本次成本×本次数量) / 新数量` 更新
`skus.moving_average_cost`；`unit_cost` 为空的行跳过该 SKU 的更新（不猜成本）；
同步更新 `docs/business-rules/master-data.md` §4 与 `inventory.md`（§86 要求）。

### T4b 暂存库位（原 Q4）

**已核实：零代码即可用。** `bin_code` 是自由字符串（`warehouse-bin.service.ts:153-177`，
显式 `binCode` 时「caller owns the string」），单建一个名为 `STAGING` 的库位
完全合法，收货选它、之后 `MOVE_BIN` 上架——规则（`inventory-dimension.ts` 三分支）
一行都不用改。

因此本项降级为**交互引导**，不做一个「功能」：

1. 收货界面选库位时，提供「暂存位」快捷选项（该仓 code 为 `STAGING` 的库位）；
2. 若该仓还没有暂存位，给一键创建入口（就是一个普通单建库位调用）；
3. 库存页对暂存位给出「待上架」视觉提示即可（派生展示，不落库）。

**不做**：批量上架（原 Q5 维持后移）、库位容量（D9 已定不做）。

## T5 验收：新商品全程走查

Sprint 7 验的是「库存能被订单消费」；Sprint 8 验的是「**一个全新商品**从零到
发货全程无断点」，且必须用**真实店铺数据**手工走一遍（集成测试覆盖规则，
真实走查覆盖体验）：

```text
1. 真实 OZON 订单进来，listing 未映射
       ↓ 断言 ORDER_SKU_MAPPING_FAILED 异常 + FAILED 行
2. Listing 页找到该未映射行 → 「建档并映射」（含生成条码、打印标签）
       ↓ 断言 Product/SKU/映射一次成型，无半成品
3. 订单行「重试解析」→ MAPPED + BACKORDERED
4. 「登记采购」→ 到货 → 扫码收货（贴上刚打印的内部条码）
       ↓ 断言库存入账、派生采购状态 已到货
5. 重试分配 → 拣货（扫同一条码）→ 发货
       ↓ 断言 On Hand 减少、订单行 SHIPPED、时限内完成
```

另做一次 Excel 闭环批量验收：导出未映射清单 ≥ 20 行 → 补填 → 双导入
（SKU → 映射）→ 抽查映射状态与重解析。

# 5. 需要用户决策的点

- **A（推荐，纳入）**：收货确认时更新 `moving_average_cost`。
  核心论据是 §3.4a 的数据安全警告：**unit_cost 不记，历史成本永久缺失**。
- **B（不纳入）**：继续只记 `unit_cost`。须自知：将来做财务（Sprint 12）
  时，早期收货的成本只能靠人工回忆补录或缺失。

若选 A，附带确认：收货界面上是否把 `unit_cost` 从「可选填」升级为
「强提示」（默认聚焦、留空给黄色警示但不阻断——留空是合法的，赠品/样品无成本）。

## 决策 3：暂存位的呈现方式（原 Q4，已降级为交互引导）

- **A（推荐）**：收货界面「暂存位」快捷选择 + 一键创建 + 库存页「待上架」

- **B**：不做任何界面改动，只在文档里写明「手工建一个名为 STAGING 的库位
  即可当暂存区用」。

## 决策 4：验收规模

- **A（推荐）**：真实数据走查 ≥ 5 个全新商品（界面路径）+ 一轮 ≥ 20 行的
  Excel 批量闭环。

# 6. 本规划不做的事

1. **不做全量 1323 条的强制清理/映射**——用户只管有货的商品（D2）；
   未映射长期存在本身不是异常（AGENTS §54 的镜像）。
2. **不新增「忽略/归档未映射」之类的新业务状态**（§98）。
3. **不做批量上架（原 Q5）**、**不做库位容量校验（D9）**、**不做自建 SN（D14）**——
   三项均已定后移/不做。
4. **不做本地打印代理**（D12 维持；待打印机型号、标签纸规格、快递系统选型
   三项信息收集齐，规划文档 §10.3.1）。
5. **不做渠道库存推送 / Allocator / 任何真实平台写操作**（Sprint 10 且需专项确认）。
6. **不做新编码规则**——建档沿用 `nextProductCode()` / `nextSkuCode()`
   集中式序号；暂存位沿用自由 `bin_code`。
7. **不做标题相似度自动匹配/自动映射建议**——映射是库存身份的锚点，
   错配代价远高于手工成本；自动化留待有真实映射数据积累后再评估（§74）。
8. **不改集成测试端口/Redis 冲突**——独立基础设施任务，另行安排
   （前一版规划 §7 已记录）。
